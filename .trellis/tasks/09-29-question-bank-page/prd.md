# 题库页：批次分组与跨批次选题再练

> **本任务是 `09-29-question-bank-tab` 的子任务**。它交付的是那个页面**上部的「我的题目」区块**
> 及其批次聚合能力；页面骨架、错题区块、tabBar 改名归父任务。

## Goal

让用户能回答「我出过的题在哪」，并把这些题**按出题批次分组**展示，支持
**批次级多选 + 展开勾单题**，把选中的题目合成一次练习再次作答。

同时消除需求 2 的根因：`batch_id` 在后端契约与响应中一直存在，前端**声明了类型却从未渲染**。

**用户价值**：用户实测原话「试着生题，但是没有反馈，我也不知道题目在哪里」——
本任务是「题目在哪里」这个问题的正面回答。

## 需求源

- 用户口述 1：「希望一个页面显示为题库，下面是题目批次分类，可以选择不同批次的题库在一起再次答题。**如果太麻烦就算了。**」
- 用户口述 2：「生题不能按批次显示归类」
- 已确认决策：选题粒度为 **批次级多选 + 可展开勾单题**（不是「勾批次就全练」）。
- 需求 2 同时登记在父批次 `09-29-field-test-fix-batch-1` 的需求 7；本任务承接后该条目不再由那个批次负责。

## 已确认事实（含证据锚点）

### F1｜`batch_id` 是无可读含义的随机码

`app/services/question.py:790` / `:1121` / `:1254`：一律 `f"batch_{uuid.uuid4().hex[:12]}"`。
**没有时间戳、没有来源、没有序号。** 所以任何批次标签都必须**推导**，不能直接显示 ID。
schema 允许它为 `NULL`（`app/schemas/question.py:101-103`「历史数据可空」）。

### F2｜一个批次可以横跨多份资料

`QuestionService.generate_questions_for_folder`（`app/services/question.py:1198`）按
`(material_id, version_id)` 保序分组，却**只生成一个** `batch_id`（`:1254`）并透传给每组
（`:1277` 传 `batch_id=batch_id`）。函数内注释原文即「跨资料单事务原子编排」。

**设计后果**：批次标签不能假定「一个批次 = 一份资料」。按资料名标注的实现在课程级出题上会给出错误信息。
反之，`generate_questions_for_knowledge_points`（`:1079`）与单考点生成（`:755`）是单一资料的。

### F3｜后端已就绪的部分（**不要重写**）

- `GET /questions` 支持 `batch_id` / `material_id` / `folder_id` / `knowledge_point_id` /
  `question_type` / `difficulty` / `review_status` 过滤，分页 `page` + `page_size`（上限 100），
  返回 `{items, total, limit, offset}`（`app/api/v1/questions.py:287-357`）。
- `POST /practices` 接受 `question_ids`，**不需要调 LLM**——这是本任务能做到「零 LLM 成本」的原因。
  与 `practiceStore.regenerateFromWrongPoints`（`src/stores/practice.ts:200-208`，要调 LLM
  且强制单一范围）是两条完全不同的路径。

> ⚠️ **本节初稿有一处被推翻的错误，保留记录以免重犯。**
> 初稿写「`question_ids` **不按 `question_count` 截断**，只需传 `question_ids` 即可」，
> 并把它标记为实测确认。**这是错的。** 显式题目路径的语义是
> **「候选题目 + 目标题数」而不是「就练这些」**：
> `app/services/practice.py:471`（RANDOM 模式先打乱）与 `:473`
> （`selected_questions = ordered_explicit[: options.question_count]`）**都会截断**，
> 而 `PracticeCreateRequest.question_count` 默认 **10**（`app/schemas/practice.py:70-75`，`ge=1, le=50`）。
> 实测：显式传 12 个 `available` 题目 id、不传 `question_count` → 练习落库 **10 题**，
> **无任何错误信号**。
>
> 成因是我当时只读到 `:462` 就下了结论，截断恰好在下一行。**半个函数的阅读不等于验证。**
>
> **对实现的约束**：调用方必须显式传 `question_count = 实际要练的题数`；
> 超过 50（`le=50`）时必须**先告知再按 50 创建**，不得静默截断。
> 这条由 AC-9 与 `design.md` 决策 4 的「更正」块共同约束。

### F4｜缺的只有「批次列表」这一个聚合能力

后端没有任何「列出批次」的接口。客户端自行分组不可行：`page_size` 上限 100，
用户题目数超过一页就要多次请求并把全部题目拉回本地才能算出批次。

### F5｜静默截断的**两条**机制（不只是待审核过滤）

原以为只有一条，实测确认有两条，且第二条更隐蔽：

1. **状态过滤**：`app/services/practice.py:441-443` 在显式题目路径上只保留
   `status == QuestionStatus.AVAILABLE` 的题目，**被过滤掉的题不报错、不入 details，请求照常成功**。
   用户勾了 20 题、其中 5 题待审核，练习里就只有 15 题，而界面上不会有任何提示。
2. **`question_count` 切片**（见 F3 的更正块）：即使全部题目都可用，
   `:473` 仍会把候选列表切到 `question_count`（默认 10）。
   用户勾 12 题、全部可用，练习里也只有 10 题。

两条都**没有任何错误信号**，且都会让「界面说 N 题、练习里 M 题」对不上。
**这是本任务最危险的失效模式**，因为它在实测里极难归因——
父批次已被同类问题坑过一次（「足迹存在」但实际少算一半）。

### F6｜跨批次练习的 `material_id` 会被自动补成「第一道题的资料」

`app/services/practice.py:590-593`：`material_id` 与 `folder_id` 都为空时，
`resolved_material_id = scattered_questions[0].material_id`。
跨批次、跨资料的练习因此会带上一个**只代表其中一份资料**的归属标签。
这不是错误（显式题目路径不校验题目是否属于该资料），但决定了「我的练习」里那条记录的观感，
所以 A 必须给出有意义的 `title`（见 design.md 决策 6）。

## Requirements

### R1 — 批次聚合接口

- 新增接口，按 `batch_id` 聚合返回本人题目批次：批次标识、题量、创建时间、来源（资料/课程）。
- 必须**服务端 group by**，不得让前端翻页拼装（F4）。
- 分页返回 `(items, total)`，与项目既有分页约定一致。
- 必须带 `user_id` 租户过滤，并排除软删除题目。
- `batch_id IS NULL` 的题目（F1）**必须能被看到**，不得静默丢弃——「题目在哪」正是本任务要解决的问题。

### R2 — 批次标签可读

- 界面上不出现 `batch_3f9a...` 这类原始 ID。
- 标签由创建时间 + 来源 + 题量推导，且必须正确处理 F2 的跨资料批次。

### R3 — 批次级三态多选 + 展开勾单题

- 每个批次一个可勾选行，状态为**全选 / 半选 / 未选**三态；全选动作作用于该批次当前可见的全部可选题目。
- 批次可展开，展开后按需加载该批次的题目列表并逐题勾选。
- **未展开的批次不得预取全部题目**（否则与 F4 的翻页拼装同病）。
- 已勾选状态在展开/收起、切换批次之间必须保持。
- 「立即开练」必须显示**已选题目总数**，且该数字与实际进入练习的题数一致（见 R4）。

### R4 — 跨批次开练

- 选中题目合成为**一次**练习，走 `POST /practices` 的 `question_ids`（F3），**不生成新题**。
- 必须处理 F5：任何不会进入练习的已选题目（`status != available`）必须**在开练前**明确告知，
  不得静默少题。
- 练习需有可读标题，使它在「我的练习」与诊断报告里可辨认（F6）。
- 创建失败必须有用户可见反馈与重试动作。

### R5 — 「生题不能按批次显示归类」的正面修复

- 核对出题页（`src/subpackages/material/pages/questions/index.vue`）必须显示本次生成的批次信息，
  使「生成了但不知道在哪」不再发生。
- 该显示须复用 R2 的标签推导，不得另写一套口径。

### R6 — 加载态、空态、故障态

- 三个状态在界面上可区分：加载中不得与「没有题目」同形；请求失败必须给出可见反馈与重试动作。
- 零题目时必须说明这是什么、题目从哪来、下一步做什么。

## Out of Scope

- **不做题目的编辑、删除、重新生成**：核对出题页已有这些动作，本区块只做「看」与「练」。
- **不做题目级搜索、按题型/难度筛选**：后端支持但用户没要，MVP 不加。
- **不做跨批次合并成「新批次」**：批次是生成痕迹，不做人为再分组。
- **不实现手动标记错题**：归 `09-29-manual-wrong-mark`；本任务只负责给它留出每题动作位的挂载点。
- **不改 `regenerateFromWrongPoints`**：那是「按错题再生新题」（要调 LLM），与本任务的「重练已有题」是两件事。
- **不给题库新增 Tab**：已确认并入学情 Tab。

## Acceptance Criteria

- [ ] **AC-1** 批次聚合接口存在，按 `batch_id` 服务端聚合；对 N 个批次只发一次列表请求即可渲染。
- [ ] **AC-2** 接口分页返回 `(items, total)`，且 `total` 为同条件的真实批次总数。
- [ ] **AC-3** 批次标签不含原始 `batch_id`；含时间、题量、来源。
- [ ] **AC-4** **跨资料批次**（F2）的标签正确：不存在「一个批次只标了其中一份资料」的错误标注。
- [ ] **AC-5** `batch_id IS NULL` 的题目出现在某个可见分组里，题量计入总数。
- [ ] **AC-6** 批次行为三态勾选；全选/半选/未选在视觉上可区分，且有用例覆盖状态推导。
- [ ] **AC-7** 展开批次按需加载：未展开的批次不发题目列表请求（用请求计数或桩验证）。
- [ ] **AC-8** 勾选状态在展开/收起与批次切换后保持。
- [ ] **AC-9** 「立即开练」显示的已选题数 == 进入练习的题数。两种静默截断机制（F5 的
      状态过滤与 `question_count` 切片）都必须被消除或**在创建前明确告知**，
      **不得静默少题**。实现要求：显式传 `question_count = 计划题数`；超过 `le=50` 上限时
      先告知再按 50 创建；服务端解析出的可用集合与界面显示数不一致时（任一方向）先告知再创建。
      **变异验证**：删掉 `question_count` 的传递后，相关用例必须失败。
- [ ] **AC-10** 跨批次练习创建成功并进入作答页；练习标题可辨认（不含 UUID 式字符串）。
- [ ] **AC-11** 核对出题页显示本次生成批次，且该标签与题库区块同一推导逻辑（同一纯函数，不重复实现）。
- [ ] **AC-12** 加载中 / 空 / 失败三态可区分，失败态有重试动作。
- [ ] **AC-13** `task verify` 全绿；新增纯函数与 store 有用例，既有用例零回归。

## Notes

- **成本判断（回答用户「如果太麻烦就算了」）**：本任务不涉及 LLM、不涉及迁移、不改判题链路。
  后端是一个只读聚合接口，前端是一个列表区块加一套选择状态。**它不麻烦**——
  建练习那一环后端本来就能用（虽然 F3 的更正块说明它的契约比初稿以为的苛刻：必须显式传
  `question_count`，否则静默砍到 10 题）。
- **本任务唯一有真实风险的点是 F5 的静默截断**（两条机制）。它们不报错，只会让用户数着题目对不上，
  而这类「少了几道」的缺陷在实测里极难归因（父批次已被同类问题坑过一次）。
  规划期我把它当成只有一条、且是低风险，**这个判断被 check 阶段推翻了**——
  `question_count` 那条才是主力，且它在 12 题这种日常量级上就会触发。
