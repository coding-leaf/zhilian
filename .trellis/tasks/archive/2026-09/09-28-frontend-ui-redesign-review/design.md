# 学习闭环修复设计

## 架构边界

后端 Pydantic 响应是 wire contract；前端在 `miniprogram/src/api/` 建立一次性、强类型的转换层，Pinia 和页面只消费归一化投影。保留现有路由与业务服务，按缺失能力补端点/字段，不让页面猜测后端字段名。

```text
上传 -> Material/Version(pending/not_started) -> 用户点击解析
     -> QueueProtocol -> Redis/RQ worker -> MaterialService.parse_material_pipeline
     -> 知识树/切片 -> 出题核对 -> PracticeService
     -> 草稿 -> 提交 -> Redis/RQ worker -> GradingService
     -> 结果页(已判/待判) -> 全判完 -> DiagnosisService -> 错题巩固
```

## 后端数据与状态

1. 资料新版本增加 `not_started` 解析状态，上传只提交资料与版本，删除服务入队和路由 `BackgroundTasks` 两条自动调度。`POST /materials/{id}/parse` 将 `not_started/failed` 原子地转为 `queued` 并入队；重试保留原有版本及权限校验。旧 `queued` 记录维持原语义，不批量取消。
2. 生产 `QueueProtocol` 的 Redis 适配改用 RQ job/registry，受控注册 `parse_material_pipeline`、`grading_jobs` 等已知任务名；内存适配器只服务测试/显式同步场景。独立 worker 从容器/开发命令启动，使用与 API 相同配置创建依赖和短生命周期数据库会话。解析/判题入口复用现有 Service，不在 Web 进程再启动一份执行。
3. RQ 负责领取、有限重试和失败登记；数据库记录是用户可见状态的事实源。任务键绑定资料版本或练习，重复领取需要幂等。达到重试上限后回写解析失败或待重判等可恢复状态，提供主动重试入口与运维日志；定期核对长期 `queued/running` 记录和 worker 存活，避免静默悬挂。RQ 的具体任务超时覆盖 OCR/LLM 的上限。
4. 交卷受理与判题完成分开：结果页从练习详情读取逐题 `grading_status` 和可空分数；正式诊断只在无待判/待重判项且 `completed_at` 已写入时生成。提交重复请求返回同一练习，诊断只生成一次。主观题自评/复查仍按现有评分服务执行，刷新后读取最终生效记录。
5. 错题接口增加稳定课程/资料归属及按课程分组/筛选的聚合结果，未分类单列；聚合覆盖完整数据而非页面第一页。再生题限定一个课程或一个未分类资料范围，显式传知识点，不跨范围混卷。
6. 头像新增受限图片上传接口，校验真实 MIME、体积及用户归属，先写对象后更新持久对象键；失败保留旧值。个人资料响应给可用的续期展示 URL，过期签名 URL 不落库。旧 `avatar_url` 数据兼容读取，迁移后的托管头像按对象键优先。

## 前端契约与交互

- 资料 adapter 映射主状态和细粒度 `parse_status`；课程列表、上传页、资料页共用同一状态文本/操作许可。上传成功停在“待解析”，只由用户命令触发解析。
- 题目 adapter 将 `question_type`、`options[{key,content}]`、来源映射到统一题型模型，预览与练习复用但预览投影不含答案/解析。后端单批上限 20：按知识点覆盖需要分批生成、去重、检查合格题覆盖，再允许进入作答；剔除/重生后重算覆盖。
- 练习 adapter 将 `items[].question_snapshot` 与 `question_id/user_answer/grading_status` 投影到卷面。每题草稿串行保存并合并快速输入，离开/交卷等待在途写入完成；失败显示可重试状态且不提交。离线本地草稿按用户和练习 ID 隔离，并以服务端确认版本恢复。
- 交卷立即跳结果页，持续读取练习详情；待判显示“判题中”，不参与已出分值统计。确认全判完才请求/展示诊断；学情页持有练习入口，退出后可重进。
- 错题按服务端分组显示，单课程直接巩固，多课程先选课程；题目助教读 `reply/suggestions`。课程助教答案中显示可点击的来源切片，失败/无证据用明确空态。
- API host 用环境配置；统一请求层在 401 时清理登录态并跳转登录，避免页面仍显示旧账号数据。

## LangGraph 使用边界

现有 `backend/app/integrations/llm/agent_graph.py` 已处理结构化 LLM 输出校验、一次修复与回退。知识提取、出题和主观题判分继续复用该图，不为解析步骤或 Redis 队列再套图。

课程助教新增一个有界 `StateGraph`：授权范围解析 -> 按资料检索并合并排序 -> 证据是否足够 -> 结构化回答 -> 引用 ID 与原始检索结果核对 -> 至多一次修复或拒答。授权和引用校验是确定性代码；LLM 不决定自己能读哪些资料，也不能凭空制造引用。题目级助教维持现有入口。图只在单次请求内运行，不在本期持久化原文或对话 checkpoint；若未来需要多轮记忆，再单独设计生命周期、隐私和保留策略。LangGraph 的状态持久化不取代启动和监控 worker。

## 兼容、迁移与运维

- `not_started` 需要数据库字段/枚举兼容性核对、Pydantic 状态字段及前端 union 同步；若是数据库字符串列，迁移重点在默认值和旧数据读法。新状态发布按后端先于前端的顺序兼容。
- RQ 任务只传 UUID/轻量标识，不携带原文或用户输入。现有自定义 Redis List 中旧任务不自动搬运；上线前停写旧队列，核对仍待处理记录并按用户可见状态重试/补派，避免丢任务。
- 头像旧 URL 保留展示兼容，但新上传改写对象键；旧对象清理只能在新对象与数据库更新均成功后进行。
- 有限重试、任务超时、worker 健康检查和积压告警是部署验收的一部分；数据错误不无限自动重试。解析、判题、诊断按业务主键设计幂等。

## 验证与风险

用真实后端响应模型序列化 fixture 固定跨层字段；测试上传无自动任务、手动触发一次、worker 消费/失败重试、交卷诊断竞态、全题型作答、草稿顺序、跨页恢复、错题分组、越权检索、伪造引用拒答、头像上传失败保留旧值。微信端到端覆盖主流程与中断恢复。执行 `task verify`，记录此前已存在的 Ruff 问题是否被修复及外部 Redis/对象存储未能测试的条件。

最大风险是旧队列无消费者导致既存悬挂任务、解析/判题重复执行、跨资料检索引用越权、以及同时修改后端模型和前端状态时的兼容窗口。每一项都以数据库状态、受控任务名和契约测试约束。
