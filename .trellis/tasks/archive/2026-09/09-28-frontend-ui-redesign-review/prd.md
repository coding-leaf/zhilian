# 前端 UI 学习闭环修复 PRD

## Goal

修复业务提交 `5d7a2f3` 的前后端契约和交互断点，使用户能从个人中心、课程资料、知识树和多题型组卷连续完成作答、诊断复查、错题巩固及真实 AI 答疑。修复范围以归档任务 `09-28-frontend-ui-redesign` 的 AC-1 至 AC-7 为准。

## Background

- 提交审查已完成，证据、逐项验收结论与门禁结果见 `research/review.md`；关键数据与状态契约见 `research/repair-contracts.md`。
- 当前工作区有大量与本任务无关的未提交更改；修复不得覆盖或回退这些内容。
- 资料状态、题目、练习、报告和助教的前端类型与后端响应不一致；以 `backend/app/schemas/*` 的真实响应为事实源，在前端统一适配。
- 上传存在双重自动解析调度：`backend/app/services/material.py:491` 入队、`backend/app/api/v1/materials.py:246` 添加后台任务；新资料版本目前写成 `queued`。
- 交卷在判题前就写 `completed`（`backend/app/services/practice.py:1106-1130`），实际全判完才写 `completed_at`（`backend/app/services/grading.py:258-270`）；诊断只按状态放行（`backend/app/services/diagnosis.py:471-486`），有提前生成未判完报告的竞态。
- 错题响应没有课程/资料标识（`backend/app/schemas/diagnosis.py:393-416`）；生成请求只接受单个资料或课程范围，跨资料题目 ID 组卷会把首题资料记作练习归属（`backend/app/services/practice.py:586-593`）。
- 归档的 `09-28-frontend-j1-contract-repair/prd.md` 已确认：所有用户选择的知识点都应覆盖；当指定题量不足时生成前说明调整，生成后披露合格题覆盖缺口。
- 默认队列配置为非即时内存队列（`backend/app/core/config.py:158-183`）；仓库内可查到解析、判题的入队代码，但没有运行时 worker/消费循环。内存适配器的 `process_next` 仅在测试中调用（`backend/app/integrations/queue/memory.py:179`），Redis 适配器目前只有入队、查状态、取消接口。若不补执行器，手动解析和异步判题仍可能一直停在待处理。
- 用户已确认采用独立 worker 执行后台解析与判题，配合 Redis 队列。现有 LangGraph 已用于知识提取、出题和主观题评分的结构化输出修复；课程助教适合新增有证据校验和拒答分支的图，LangGraph 不替代队列执行器。

## Requirements

### R1 个人资料与课程管理

- 用户可查看、修改并持久化昵称；点击头像可选择图片上传至应用托管存储，刷新或重新登录后仍能显示。上传失败不得覆盖旧头像；不再要求手填图片 URL。
- 工作台可创建、重命名和归档课程，显示课程资料与考点统计；危险操作需确认，课程切换后展示正确资料范围。

### R2 资料解析与知识学习

- 上传到课程后只持久化资料和版本，不自动解析或入队；UI 显示“待解析”。用户点击“开始解析”才调度，期间可见进度与失败原因，完成后可进入知识树与原文切片。失败重试属于用户主动操作，可以重新调度。
- 统一识别后端 `pending/parsing/ready/failed/retake_required` 及版本细分状态。已有待处理、处理中和失败资料在升级后应正确展示，不把未启动版本标为已排队。
- 知识点详情显示真实定义、层级和来源切片；无来源或失败时给出准确状态，不伪造解释。

### R3 出题核对与组卷

- 支持按课程或资料多选知识点、题型、题量和难度。题型至少覆盖单选、多选、判断、填空、名词解释、简答和案例分析；请求遵守后端单次 1 至 20 题的限制。
- 预计题量至少为 `max(已选知识点数, 用户指定题量)`；如需调整，生成前向用户说明。最终合格题须核对实际考点覆盖；不足时显示缺口，不把生成目标当成覆盖成功。
- 核对页展示题干、选项和来源，不提前展示标准答案与解析；可剔除或重新生成不合适的题。剔除后仍须满足已选考点覆盖才能开始作答。

### R4 练习作答与恢复

- 将后端 `items[].question_snapshot` 映射为统一卷面模型；七种题型可正确显示选项或输入控件，并使用后端要求的 `question_id/user_answer` 保存草稿。
- 同题草稿写入需有序、失败可见，交卷前确认所有待保存答案已成功写入；未答确认与稳定的提交幂等键生效。关闭并重进后可从学情页恢复本人未完成练习，答案不丢且不串账号。

### R5 结果、复查与诊断

- 交卷后立即进入结果页，显示已判结果与未判题目的“判题中”；待判项不显示为零分或答错。用户可离开并从学情页再次打开。
- 正式诊断仅在真正全卷判完后生成和展示；后端须堵住交卷受理后、异步判题前提前生成报告的竞态。逐题结果、总分、薄弱点、原文依据使用真实练习详情和诊断数据组合。
- 主观题展示得分、采分点与判题状态；支持真实自评或填写理由申请 AI 复查，复查后刷新生效结果。错误、超时与待重判状态可恢复。

### R6 错题巩固

- 错题本按课程归类；只有一个课程时可直接针对该课程巩固，涉及多个课程时先选课程，未分类资料单独归类。分组统计应覆盖完整分页数据。
- 从报告或错题本再生题时传入正确课程/资料范围和错题考点；跨课程错题不得混成错误归属的单课程练习，生成后可进入新一轮作答。

### R7 AI 助教

- 题目级助教正确展示后端 `reply/suggestions`，在题目解析或报告中可追问。
- 课程/资料/知识点级助教必须基于当前用户有权访问的相关切片回答并展示来源；无证据或服务失败时明确告知，不以固定模板文案冒充 AI 答疑。
- 课程助教的检索、证据充分性判断、答复与引用校验形成有界工作流；只能引用本次授权检索返回的切片，校验不通过时至多修复一次，仍失败则拒答。

### R8 运行与验证

- API 地址由环境配置，开发可连本机，真机可连可访问的 HTTPS 服务；登录过期时网络层与 Pinia 登录态一致。
- 使用真实后端序列化响应样本覆盖前端适配、异步状态、断网/重试和跨页恢复；补后端接口/服务测试及微信端到端学习流程。修复既有 Ruff 错误，使 `task verify` 完整通过。

## Acceptance Criteria

- [ ] AC-1：昵称、选图头像可保存并在重新登录后显示；课程可创建、重命名、归档，资料可上传到指定课程。
- [ ] AC-2：上传后没有自动解析任务；手动启动后可见状态流转，最终能打开真实知识树、知识点详情及切片；失败可主动重试。
- [ ] AC-3：多考点、多题型、题量和难度配置可用；题量调整与覆盖缺口明确；核对页可剔除/重生题目，作答前不展示答案与解析。
- [ ] AC-4：七种题型可作答与保存；慢网络下最后一次答案不会丢失；未答确认、重复提交、离开后恢复均正确。
- [ ] AC-5：交卷后立即可见真实判题进度；全判完后才有正式诊断；主观题可自评或申请复查，刷新后显示最终生效结果。
- [ ] AC-6：错题按课程和未分类来源正确归类；选定范围后可针对错题考点再生题并进入新练习。
- [ ] AC-7：题目及课程助教返回真实、当前用户有权访问范围内的答复；课程答复有可查看的来源，失败时不显示伪造内容。
- [ ] AC-8：前后端契约测试、微信端到端主流程与中断恢复通过，`task verify` 全部通过；测试证据与未能验证的外部服务条件记录清楚。
- [ ] AC-9：手动解析与交卷判题任务在部署配置下确实被执行；进程重启或任务失败后能定位状态并恢复，不出现永久待处理且无提示的记录。
