# 实测缺陷修复批次（第一批）：需求地图与总验收

## Goal

把一次真机/开发者工具实测暴露的 5 类功能缺陷收敛成有顺序、可独立验证的修复集，
使「上传资料 → 解析就绪 → 选题出题 → 作答判题 → 学情沉淀」这条主链路在实测环境里真正跑通。

本任务是**父任务**：持有需求源集合、任务地图、跨子任务验收标准与最终集成复核。
它本身不是实现目标——除 `prd.md` 外不改任何代码。

## 需求源（2026-09-29 用户实测口述，原文保留）

1. 「工作台界面我发现无法创立新课程，或者说，有关文字输入框的我都无法操作，包括新建课程、ai助教、资料内的ai助教，想输入文字，结果会自动消失（不排除是微信开发者助手的问题）」
2. 「我有一个一小时前上传的文件，一直在解析，没有返回资料」
3. 「我还在已有资料解析的资料，试着生题，但是没有反馈，我也不知道题目在哪里」
4. 「学情界面，意义不明？感觉可能要重新设计，不排除因为前面链路阻断导致我无法使用」
5. 「我的部分，学习足迹为 0」
6. （追加，同日实测）「`POST /questions/generate` 502：`大模型服务返回异常状态码: 400`」——
   用户按建议把 LLM 切到 DeepSeek 官方 API 后暴露的既有兼容性缺陷（思考模式不支持强制
   `tool_choice`），见 [09-29-fix-llm-thinking-mode](../09-29-fix-llm-thinking-mode/prd.md)。
7. （追加，同日实测，**登记未实现**）「生题不能按批次显示归类」——`batch_id` 在后端契约与
   接口响应中均存在，前端仅声明类型、**从未渲染**，属从未实现而非回归。
8. （追加，同日实测，**判定为下游症状**）「选择题也要判题，不该秒出么」——
   交卷后判题**全部异步入队**（`services/practice.py:1145` `enqueue("grading_jobs")`），
   而 worker 在本机不可用（见子任务 2），故所有题停在「判题中」。
   **不是「客观题判得慢」**。worker 恢复后仍存在秒级异步延迟；是否改为交卷时同步判客观题，
   属设计决策，需单独评估。

## 为什么这样切分

- **需求 1 单独成任务**：它是唯一的**全局**缺陷——同一现象横跨工作台弹窗、AI 助教抽屉、资料页助教、
  个人中心弹窗四处，任何一处都不是独立 bug。按页面拆会把同一个根因修四遍。
- **需求 2 单独成任务**：它是**前后端各占一半**的缺陷。后端缺 worker 消费与重派通道，前端缺超时反馈与逃生入口。
  只修一侧，用户依然卡死。
- **需求 3、5 一度被假定为需求 2 的下游，规划阶段的证据推翻了这一假定**：
  - 需求 3 的真因是 `questions/index.vue` 的 `isConfigMode` **没有任何一处被写成 `false`**，
    导致预览区（生成的题目、覆盖缺口、「开始作答」）是**不可达的死代码**。
    用户实测用的是**已解析资料**，该缺陷与解析链路无关。
  - 需求 5 的真因是个人页统计**只对课程级聚合求和**，`folder_id IS NULL` 的资料被静默排除。
    当前环境已可复现：用户持有 4 份 `ready` 资料，统计最多只算 1 份。
  - 因此两者**都不必等需求 2**。这条修正本身是本批次规划的产出之一，
    记在这里是为了说明：**父任务在收口时也同样要重核「下游后果」这类未经证实的归因**。
- **需求 4 单列并加门禁**：它可能只是需求 2 的下游，也可能是真实的信息架构问题。先修链路再判断，
  避免把「没数据」误诊成「设计烂」。

## 跨子任务验收标准

以下标准不属于任何单个子任务，只有父任务在收口时统一核对。

- [ ] **XAC-1 主链路端到端跑通**：在实测环境（开发者工具 + 真机各一次）走完
      「新建课程 → 上传资料 → 解析到 `ready` → 选中考点出题 → 开始作答 → 交卷看到判题结果」，
      全程不需要重启进程、不需要删除重传资料、不需要手动改库。
- [ ] **XAC-2 每一处「卡住」都有可见出口**：链路上任意一步失败或超时，用户界面上都能看到
      「发生了什么 + 我能做什么」，不存在只有转圈或只有一句无信息量文案的死角。
- [ ] **XAC-3 没有任何一处输入框在无用户操作的情况下丢失已输入内容**：四处输入点
      （工作台新建课程、AI 助教抽屉、资料页助教、个人中心昵称）逐个验证。
- [ ] **XAC-4 空态与故障态可区分**：「没有数据」和「拉取失败」在文案与视觉上必须不同。
      这一条同时约束 `learning-stats` 与 `review-page-ia`。
- [ ] **XAC-5 门禁全绿**：`task verify` 退出码 0（后端 ruff / mypy / lint-imports / pytest，
      前端 eslint / vue-tsc / vitest），且各子任务不引入既有用例回归。
- [ ] **XAC-6 环境结论留档**：本次实测所在环境已留档一个**非本仓库**的故障
      （微信开发者工具网络层未把请求字节发出，见 `09-29-login-request-hardening` 的 Notes）。
      凡在本批次中被判定为「环境而非代码」的现象，必须在本任务 Notes 中写明判定依据，
      避免下次实测把它当成新 bug 重查。

### 环境结论（**重要，不要再走回头路**）

- **部署目标是 Linux/Docker**，由用户明确确认。**Windows 不是后端 worker 的目标平台**，
  「RQ 2.12 在原生 Windows 上不可用」这一结论虽然成立，但**前提本身就是错的**——
  不需要在 Windows 上跑 worker，也**不要在 Windows 上继续给 RQ 打补丁**。
- `app/worker.py` 里保留的两处 `os.name == "nt"` 守卫补丁**经用户确认保留**
  （POSIX 侧零影响，把排查结论留在代码里）。**不要删除，也不要扩展。**
- `deploy/docker-compose.yml` **本来就定义了 worker 服务**；本批次的「解析全卡住」根因是
  **该服务从未启动**（postgres / redis / minio 都是这套 compose 起的，唯独 worker 没起）。
- 容器构建曾因 **Docker 守护进程拿到被污染的 DNS**（解析 `registry-1.docker.io` 到
  `185.45.7.185`，而 Windows 侧解析到正确的 AWS 地址）而拉不到 `python:3.13-slim`。
  用户决定**开 xray 的 TUN 模式**解决，**不再配置 Docker 代理**。用户自行执行
  `docker compose up -d worker`。
- 侦察期间验证链路可用所跑的 **WSL worker 是会话级后台进程，会随会话结束而消失**；
  它只用于验证，**不是常驻方案**。常驻方案以容器为准。
