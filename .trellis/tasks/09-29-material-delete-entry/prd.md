# 资料删除入口

## Goal

让用户能删掉不再需要的资料。后端**早已具备**软删除能力，前端**一个入口都没有** ——
这就是「资料没有删除键」的全部原因。本次只补前端入口，不动后端。

## 需求源

用户（2026-09-29）：「我发现小问题,资料没有删除键」。
背景：用户此刻的目标是「交付一个功能完整可用的软件」，这是其中一个小缺口。

## 已确认事实（证据锚点）

- `DELETE /materials/{material_id}`（`app/api/v1/materials.py:770-790`）：**软删除**，
  置 `is_deleted=True`，**保留历史答题记录**。
- `DELETE /materials/{material_id}/hard`（`app/api/v1/materials.py:725-757`）：物理级联销毁，
  连对象存储文件一起清。
- 前端 `src/api/index.ts` **没有任何资料删除函数**（两处 `method: 'DELETE'` 分别是
  归档课程与错题删除）—— 缺口纯在前端。
- 列表默认过滤软删除（`app/repositories/material.py:108` 的 `is_deleted == False`），
  故软删除后资料从列表消失。
- ⚠️ **没有恢复接口**：`is_deleted=True` 之后**没有任何 API 能改回来**
  （`grep restore` 在 material 的路由与服务里零命中）。所以后端响应里那句
  「资料已移至回收站」是**空头承诺**，前端**不得照抄**。
- 既有交互模式可沿用：工作台「归档课程」= `folder-action-danger` 文字动作
  （`src/pages/index/index.vue:54`）+ `uni.showModal` 确认（`:297-305`）+ 成功 toast。
  资料卡在 `:97-99` 的 `v-for="item in materialStore.materialList"` 里。

## 用户已确认决策（2026-09-29）

| 决策点 | 取值 |
| --- | --- |
| 删除力度 | **软删除**（不是硬删除） |
| 立项方式 | 轻量任务，PRD-only |

选软删除的理由：硬删除会级联销毁对象存储文件，且引用它的错题与学习足迹一起受影响；
而用户正在意统计口径的准确性。软删除也是唯一能**后续补上「回收站 + 恢复」而不丢数据**的方案。

## Requirements

### R1 — 入口与交互与既有模式一致

- 资料卡上有删除入口，形态对齐「归档课程」：danger 文字动作 + `uni.showModal` 确认 + 结果 toast。
- 不发明新的交互（不做滑动删除、不做长按菜单）。

### R2 — 只走软删除

- 只调 `DELETE /materials/{id}`，**不碰** `/{id}/hard`。

### R3 — 确认文案必须诚实

- **不得出现「回收站」**：没有恢复接口，说了就是骗用户。
- 文案必须让用户知道：删除后不再显示、**历史作答记录保留**、且**当前无法在应用内恢复**。

### R4 — 失败可见

- 删除失败必须有用户可见反馈与可重试路径，**不得静默**。
- 错误分类走 `src/utils/requestError.ts` 的 `RequestError` / `RequestErrorKind`，
  不按 `error.message` 字符串判断。

### R5 — 成功后列表即时更新

- 成功后就地移除该资料，不要求整页重载。

### R6 — 契约层

- `src/api/index.ts` 增 `apiDeleteMaterial(materialId)`，适配器归一化响应。

## Out of Scope

- **不做硬删除入口**（见决策理由）。
- **不做回收站视图，也不做恢复接口**：那需要后端新增能力，是另一个量级。
  本任务只保证文案**不谎称**存在回收站。
- **不改后端**：本次零后端改动。
- **不做批量删除**。

- [ ] **AC-5** 取消确认时**不发任何请求**；用例覆盖。
- [ ] **AC-6** 连点不会发两次删除请求（在途守卫）。

  「不含回收站」断言要一并调整——不要只改文案而留下一个说反话的测试。
