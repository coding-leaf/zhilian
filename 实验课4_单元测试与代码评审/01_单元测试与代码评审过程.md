## 2 单元测试过程

### 2.1 设计方法（4 步强制）

按 `docs/测试设计规范.md`，每批用例必须完成：

1. **等价类划分**：有效/无效等价类逐项列出（如错误码映射 41 项参数化）；
2. **边界值分析**：空值 / 单元素 / 阈值上下相邻（如状态机 6 状态、分页 ge=1/le=100）；
3. **错误推测**：基于历史缺陷推测易错点（如 `detail` 别名、状态泄漏）；
4. **路径覆盖**：核心分支逐条走通（算法核分支覆盖 99.7%）。

### 2.2 用例规模与质量

| 项 | 数值 |
| --- | ---: |
| 测试文件 | **100 个** |
| 测试用例 | **1616 个**（1616 passed / 3 skipped / 0 failed） |
| 单元测试耗时 | **20.23 秒**（全部单元测试 30 秒红线内） |
| 全量耗时（含集成） | **46.27 秒**（不依赖数据库与网络） |
| 断言质量 | 每用例至少一处断言；3 处「锁定 bug 行为」的用例在评审中被拦截并修正 |

### 2.3 覆盖率（权威口径，2026-10-05）

> 口径：`uv run pytest tests --cov=app --cov-branch` + `coverage report`（语句+分支综合）；
> 排除清单四类（启动装配/任务入口/迁移环境/Pydantic 模式目录）集中维护在 `backend/pyproject.toml`。

| 范围 | 阈值（文档） | 实测 | 判定 |

| 全局 行覆盖 | ≥ 80% | **95.5%** | ✅ |
| 全局 分支覆盖 | ≥ 70% | **86.9%** | ✅ |
| 算法核 行 / 分支 | ≥ 95% / ≥ 90% | **99.9% / 99.7%** | ✅ |

## 3 代码评审过程

### 3.1 评审准备（作者自检 + PR 拆分）

| 项 | 实录 |
| --- | --- |
| 自检 | 8 项自检（命名/注释/日志/异常/安全/性能/重复/单测）→ `代码评审与提交/自检记录.md` |
| PR 拆分 | **4 个 PR**：323 / 202 / 291 / 194 行（均 ≤ 400 行，避免「一次上千行」） |
| PR 描述 | 变更内容 + 关联需求/缺陷 + 测试情况 + 影响范围 + 风险点（模板：`.github/PULL_REQUEST_TEMPLATE.md`） |
| 自动检查 | 9 项门禁在提审前全绿 |
| 评审人分配 | 3 名评审人（SecLead / TechLead / Reviewer），关键模块含架构视角 |

### 3.2 评审执行

| 项 | 实录 |
| --- | --- |
| 形式 | 核心模块开评审会（85 分钟），其余在线评论 |
| 检查清单 | 正确性 / 设计 / 可读性 / 健壮性 / 安全 / 性能 / 测试充分性 / 可观测性 / 文档（9 项） |
| 问题分级 | 🔴 阻塞 **3** / 🟠 重要 **9** / 🟡 建议 **16**（共 **28** 条） |
| 结论 | 4 个 PR 均为「修改后通过」→ 修复 → 复评通过 |

### 3.3 问题闭环（100%）

| 级别 | 数量 | 处置 |
| --- | ---: | --- |
| 🔴 阻塞 | 3 | 全部修复 + 原评审人复评 ✅ |
| 🟠 重要 | 9 | 全部修复 + 复评 ✅ |
| 🟡 建议 | 16 | 5 项本轮闭环 + 11 项登记 M1 技术债（100% 有处置） |

### 3.4 评审有效性数据

| 来源 | 问题数 | 说明 |
| --- | ---: | --- |
| 机器门禁 | 4 | lint / format（人工不易逐一发现） |
| 人工评审 | 24 | 设计 / 契约 / bug / mock 反模式 |
| **仅人工可发现** | **5** | mock 反模式 / 状态泄漏 / 异常过宽 / 评审措辞 / 状态机边界 |
