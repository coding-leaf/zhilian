## 2 基线 tag

| 项 | 值 |
| --- | --- |
| tag 名称 | `midterm-baseline-2026-10-03` |
| tag 类型 | **附注 tag**（`git tag -a`），带说明信息，可用 `git show` 追溯基线含义 |
| 目标提交 | 提交本次改动后的 `master` HEAD |
| 命名理由 | 不使用 `v*` 前缀——本项目尚未进入「版本发布」里程碑，「v0.x」会与之混淆 |

```bash
# 1. 先提交（示例；请按仓库规范写提交信息）
git add -A
git commit -m "ci(ci): 接入覆盖率留档、SonarCloud 与 PR 模板，并准备中期基线"

# 2. 打附注 tag
git tag -a midterm-baseline-2026-10-03 -m "中期质量检查基线：自 2026-09-29 收敛起点起"

# 3. 推送 tag（分支保护不拦 tag，但需显式推送）
git push origin midterm-baseline-2026-10-03

# 4. 核对
git tag -l "midterm-*"
git show --stat midterm-baseline-2026-10-03 | head -20
```

## 4 为什么不用「ZL-143」表达范围

《开发过程文档》§6.2 写的收敛起点是「2026-09-29（提交 `ZL-143` 起）」。
但实测：

```bash
git log --oneline --all --grep="ZL-143"    # → 空
```

**`ZL-143` 是任务编号，不在任何提交信息里。** 用它表达范围**不可复现**——
不同人执行会得出不同结果。因此本基线改用**可复现的 commit 边界**（`61b9ee1..HEAD`）。

这是第 1 步立下的纪律「数字不手抄、结论要附命令」的一次实际应用：
**一个不可复现的范围定义，等于没有范围定义。**

## 5 与《评审清单》的关系

本文件定义「**评审哪些提交**」，《评审清单》定义「**这些提交里的哪些模块怎么查**」。

| 文档 | 回答的问题 |
| --- | --- |
| 本文件 | 范围边界在哪、多少提交、多少文件 |
| 《评审清单》 | T0/T1/T2 分别查什么、放行规则是什么 |
| 《单测计划》 | 覆盖率怎么算、测哪些、墙钟抖动怎么办 |
| 《中期质量计划》 | 为什么这样查、谁查、什么时候查完 |

范围切片方式：`git diff --name-only` 的输出按模块归类后，与《评审清单》的
T0（核心业务 / 高风险）/ T1（常规）/ T2（低风险）三档对应。

## 7 注意事项

1. **基线必须是绿的**。如果 tag 指向的提交 CI 未跑绿，这个基线就没有「已知良好」的含义，
   后续所有「相对基线的回归」判断都会失去参照。
2. **tag 不随分支移动**。打完之后 `master` 继续前进，基线仍固定在原提交——这正是它的用途。
3. **不要用 `git push --tags`** 批量推：远程仓库当前**一个 tag 都没有**（实测
   `git ls-remote --tags origin` 输出为空），而本地存在 `backup/session-2026-09-28-before-trellis`
   这类备份 tag，批量推会把它们一并推上远程。**按名推送**（第 2 节第 3 步）。
4. **历史偏差不追溯改名**（`docs/开发过程文档.md` §6.1）：`feat/*`、`codex/*` 等历史分支名保留原样。
