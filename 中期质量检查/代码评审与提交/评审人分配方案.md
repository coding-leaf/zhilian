## 4 评审人决策流程

```
PR 提交
   ↓
GitHub 自动请求评审（依据 CODEOWNERS）
   ↓
┌──────────────────────────────────┐
│ 主评审人 Reviewer/SecLead        │ ← 先评审
│  ├─ 通过 → 提交加签人            │
│  └─ 不通过 → 请求修改             │
└──────────────────────────────────┘
   ↓
┌──────────────────────────────────┐
│ 加签人 / 副评审人 SecLead/TechLead│ ← 复审
│  ├─ 通过 → PR 进入合并环节        │
│  └─ 不通过 → 请求修改             │
└──────────────────────────────────┘
   ↓
所有评审人 approve + CI 全绿
   ↓
合并按钮可点击
```

> **关键规则**：
> - 任何评审人 approve 为通过，**全部评审人** approve 为合并前置条件
> - CI check（`verify.yml` 三 job 全 green）是合并**必经环节**
> - 评审人 approve 但 CI 不通过 → **禁止合并**
> - CI 通过但评审未完成 → **禁止合并**

## 6 评审人协作约定

### 6.1 评审优先级（来自 `docs/团队分工.md` §3）

| 优先级 | 情形 | 处理 |
| :---: | --- | --- |
| P0 | 测试可重复运行性、可信度 | Reviewer 优先 |
| P1 | 错误模型、状态机语义 | SecLead 优先 |
| P1 | 业务口径、需求边界 | TechLead 优先 |
| P2 | 工程效率、可观测性 | DevOpsLead 优先 |

### 6.2 评审人不通过的情形（必填原因）

| 情形 | 处置 |
| --- | --- |
| 命名不符合规范 | 注明行号，要求修改 |
| 注释缺失或错误 | 注明位置，要求补充 |
| 异常处理不充分 | 注明场景，要求补充 |
| 测试覆盖不充分 | 注明缺失的等价类/边界值 |
| 安全漏洞（横向越权、注入等） | 立即 Block PR，要求修复 |

### 6.3 评审通过的条件

- ✅ 所有自动化检查通过（CI + 单测 + Lint + 静态扫描）
- ✅ 主评审人 + 加签人均 approve
- ✅ 评审意见全部 resolved（`Resolve conversation`）
- ✅ PR 描述完整（变更/关联/测试/影响/风险五段）

## 7 评审完成后

| 项 | 触发 |
| --- | --- |
| 合并到 `dev` 分支 | 双人 approve + CI 全绿 + 描述完整 |
| 合并到 `master` 分支 | 需 TechLead 最终签字（PR 模板已写明） |
| 文档同步 | 合并后通知 Reviewer 更新《单测计划》《覆盖率报告》|

> **合并门禁**：任何 PR 缺少评审人签字或 CI 不绿，**GitHub 拒绝合并按钮**（分支保护规则实现）。
