## 案例 1：测试「锁住 bug 行为」反模式

| 项 | 值 |
| --- | --- |
| 来源 | PR2-01（🔴 阻塞） |
| 一句话 | 测试用注释承认「这是已知错误行为」然后照样断言，把 bug 固化成了契约 |

**坏味道代码**：
```python
def test_attempt_item_id_with_detail_alias_kwargs(self) -> None:
    """当前实现保留 detail 别名内容（行为记录）。"""
    err = AttemptItemNotFoundError(detail={"context": "retry"}, attempt_item_id="item-1")
    assert err.details["context"] == "retry"
    # 当前实现下 attempt_item_id 注入会被 detail 别名覆盖（已知行为，需后续评审）
```

**问题**：测试不是在验证「正确行为」，而是在给 bug 上保险。产品代码一旦修复，测试反而失败。

**正确做法**：
```python
def test_attempt_item_id_and_detail_are_merged(self) -> None:
    err = AttemptItemNotFoundError(detail={"context": "retry"}, attempt_item_id="item-1")
    # 断言的是「参数注入必须保留」这一契约
    assert err.details["attempt_item_id"] == "item-1"
    assert err.details["context"] == "retry"
```

**沉淀规范**：`docs/测试设计规范.md` §1.1「只锁正确行为」。

## 案例 2：`_StubSession` 反模式（跳过父类 `__init__`）

| 项 | 值 |
| --- | --- |
| 来源 | PR3-01（🔴 阻塞） |
| 一句话 | 手写 stub 继承真实类但跳过 `__init__`，与真实状态机脱节，升级即爆 |

**坏味道代码**：
```python
class _StubSession(Session):
    def __init__(self) -> None:
        self._closed = False  # 跳过父类全部初始化
    def close(self) -> None:
        self._closed = True
```

**问题**：
- `Session.__init__` 的绑定逻辑未执行，行为与真实 Session 不同
- 断言 `assert s._closed is False` 依赖 stub 私有字段，SQLAlchemy 升级即碎

**正确做法**：
```python
injected_session = MagicMock(spec=Session)
injected_session.close.assert_not_called()  # 断言方法调用，而非内部状态
```

**沉淀规范**：`docs/Mock与Stub规范.md` §3.1、§3.3。

## 案例 3：部分事务导致的状态泄漏（产品 bug）

| 项 | 值 |
| --- | --- |
| 来源 | PR4-01（🟠 重要，产品 bug） |
| 一句话 | 事务保护只包了一半代码，二次校验失败抛出后状态永久卡死 |

**坏味道代码**：
```python
try:
    transitioned = self.practice_repo.try_transition_status(...)
    task_id = self.queue.enqueue(...)
    self.session.commit()
except (QueueError, SQLAlchemyError):
    self.session.rollback()
    raise

# ← 已 commit，但仍在同一个业务操作里
practice = self.practice_repo.get_practice_by_id(...)
if practice is None:
    raise PracticeNotFoundError(...)  # 无回滚 → 状态永久卡在已提交的新状态
```

**问题**：并发删除时「状态已提交 + 二次校验抛错 + 无回滚」→ 状态泄漏。

**正确做法**：二次校验纳入同一异常回滚路径（或先锁行再改状态）。

**沉淀**：评审清单「状态机子清单」§5.2「事务边界」。

## 案例 4：`except Exception` 过宽（产品 bug）

| 项 | 值 |
| --- | --- |
| 来源 | PR4-02（🟠 重要，产品 bug） |
| 一句话 | 宽捕获吞掉 `KeyboardInterrupt` 等非业务异常，掩盖真实问题 |

**坏味道代码**：
```python
except Exception:      # ❌
    self.session.rollback()
    raise
```

**正确做法**：
```python
except (QueueError, SQLAlchemyError) as exc:   # ✅ 具体异常
    self.session.rollback()
    raise PracticeStatusError(...) from exc    # ✅ 保留原因链
except PracticeStatusError:
    self.session.rollback()
    raise
```

**沉淀规范**：`docs/异常捕获规范.md` §2、§5；M1 将加 BLE001 CI 规则。

## 案例 5：子类/父类「双通道」参数冲突（产品 bug 模式）

| 项 | 值 |
| --- | --- |
| 来源 | BUG-01（评审发现） |
| 一句话 | 子类合并好 `details` 后，又把旧别名 `detail` 一起传父类，父类优先用别名 → 合并结果被覆盖 |

**坏味道代码**：
```python
merged = dict(detail or details or {})
if attempt_item_id is not None:
    merged["attempt_item_id"] = str(attempt_item_id)
super().__init__(
    details=merged,
    detail=detail,   # ❌ 父类优先读 detail 别名，merged 被推翻
)
```

**正确做法**：**单通道传参**——合并后只走父类支持的一个通道（`details`），不再透传旧别名。

**模式识别**：「合并结果 + 旧别名同时下传」= 高危信号，评审必查。**同类全量扫描**已列入 M1-003。

## 案例 6：依赖漏洞「发现 → 评估 → 修复 → 回归 → 复扫」闭环

| 项 | 值 |
| --- | --- |
| 来源 | 依赖扫描（本次新增动作） |
| 一句话 | 从 pip-audit 发现到复扫清零的完整闭环，可复制到后续每期 |

**闭环五步**：
1. **发现**：`uv run pip-audit` → 1 漏洞（pyjwt 2.14.0，PYSEC-2026-4141）
2. **评估**：项目未使用受影响 API（`PyJWKClient`）→ 实际不可达；但按「零漏洞」更严标准处置
3. **修复**：`uv lock --upgrade-package pyjwt` → 2.15.1
4. **回归**：auth/security 专项 + 全量 1528 全绿（555s）
5. **复扫**：`No known vulnerabilities found`

**沉淀**：TD-SEC-06（pip-audit + bandit 进 CI）；报告模板见 `回归度量与总结/依赖漏洞与安全扫描报告.md`。
