## 1 目标

1. **新增/改动代码有测试锁住**：增量覆盖率达标，且断言真的锁行为（过覆盖率 ≠ 锁行为）。
2. **前端从"无覆盖率"到"有度量"**：先接入工具，再设阈值，避免用错基线。
3. **"通过率 100%"可稳定取证**：正面处理 E-1 墙钟抖动，不放宽阈值。
4. **测试不慢、不依赖外部服务**：沿用"外部能力走协议抽象 + 内存假实现"的既有设计，
   保持全量秒级跑完（依据：`docs/开发过程文档.md` §5.2——测试慢是覆盖率下滑的第一原因）。

## 2 覆盖率口径

### 2.1 增量口径（本期准出主线，QG-2 / QG-3）

```
增量覆盖率 = 本次改动中被用例执行到的可执行行数 / 本次改动中的可执行行总数 × 100%

其中「本次改动」= git diff（当前分支 vs origin/master）的新增/修改行；
可执行行 = 排除空行、纯注释、纯文档（.md）后剩余的行。
```

| 适用范围 | 口径 | 阈值 | 实现 |
| --- | --- | --- | --- |
| 后端：所有改动行 | **增量** | **≥ 80%** | `diff-cover`（QG-2） |
| 后端：T0 核心 `app/core/{algorithms,security,errors}` | **绝对** | **≥ 90%** | `coverage report --include`（QG-3） |
| 后端：T0 接口层 `app/api/deps/` | **绝对** | **≥ 80%**（目标 90%） | `coverage report --include`（QG-3） |
| 前端：所有改动 | 增量 | **≥ 80%**（工具接入并观察一个里程碑后启用） | 待定（QG-2） |

> **关于 T0 的口径**：原方案是「T0 也用增量、阈值 90%」，实现时发现 diff-cover 的 `--include`
> 在本项目布局下不可用（详见 §3.1 实测坑），且它失败的方式是**静默放行**。
> 因此 T0 改用**绝对覆盖率**考核 —— 这也更贴合课程原文「核心模块 ≥ 90%」的表述
> （「新增代码覆盖率」对应增量、「核心模块 ≥90%」对应绝对）。
> 两种口径并存：全量防倒退、增量防漏测、T0 绝对防核心退化。

| 具体的后端阈值 | 值 | 现状 |
| --- | --- | --- |
| 全量 `app/` | ≥ 80% | 实测 **91%** ✅ |
| T0 核心三处 | ≥ 90% | 实测 **99%** ✅ |
| T0 接口层 `api/deps/` | ≥ 80%（目标 90%） | 实测 **83%** ⚠️ 未达 90% |

### 2.2 全量口径（L1 硬门禁，不变）

| 端 | 口径 | 阈值 | 现状 |
| --- | --- | --- | --- |
| 后端 | `app/` 全量、含分支覆盖 | ≥ 80% | 实际 91%+（`Taskfile.yml`） |
| 前端 | 暂无 | 暂无 | 本期接入后观察 |

> **两套口径并存**：全量防倒退、增量防"新代码不测"。增量**叠加**在全量之上，不替换。

## 3 工具与命令

### 3.1 后端增量覆盖率（`diff-cover`）—— **已接线（2026-10-03）**

```bash
cd backend
uv run pytest tests --cov=app --cov-branch --cov-report=xml
uv run diff-cover coverage.xml --compare-branch=origin/master --fail-under=80
```

已接进 `Taskfile.yml` 的 `verify-backend` 与 `.github/workflows/verify.yml`（两边命令**逐字一致**）。
CI 侧 `actions/checkout` 已设 `fetch-depth: 0` —— 浅克隆里没有 `origin/master`，
diff-cover 会直接抛 `Could not find the branch to compare to`，门禁会红而不是静默通过。

**T0 加严不用 diff-cover 的 `--include`，改用 `coverage report`：**

```bash
# T0 核心模块（app/core）绝对覆盖率 ≥90%
uv run coverage report --include="app/core/algorithms/*,app/core/security.py,app/core/errors.py" --fail-under=90
# T0 接口依赖层 ≥80%（当前 83%，目标 90%）
uv run coverage report --include="app/api/deps/*" --fail-under=80
```

> ⚠️ **实测坑（2026-10-03）：diff-cover 的 `--include` 在本项目布局下永不匹配。**
> 它的实现是把 `glob.glob(pattern)` 的结果与 diff 解析出的 `src_path` 做**相等比较**，
> 而 `src_path` 是 **git 根相对**路径（`backend/app/core/errors.py`）、`glob` 是**当前目录相对**——
> `Taskfile` 的 `dir: backend` 让两者天然错位。`backend/app/...`、`app/...`、`**/app/...`
> 各种写法都实测过，全部不匹配。
> 后果不是报错，而是输出 `No lines with coverage information in this diff.` 并 **exit 0**，
> 即**静默放行**——这比没有门禁更危险，它会让人以为「T0 已加严」。
> 因此分模块加严一律用 `coverage report --include`（基于 fnmatch，跨平台可靠，已实测能正确判失败）。

**2026-10-03 实测基线**：

| 范围 | 实测覆盖率 | 门禁阈值 | 状态 |
| --- | --- | --- | --- |
| 全量 `app/` | **91%** | ≥ 80% | ✅ 通过 |
| T0 核心 `app/core/{algorithms,security,errors}` | **99%** | ≥ 90% | ✅ 通过 |
| T0 接口层 `app/api/deps/` | **83%** | ≥ 80%（**目标 90%**） | ⚠️ **未达标** |
| 增量（改动行） | 本次改动不含 Python 代码，无从判定 | ≥ 80% | — |

> **`app/api/deps/` 未达 90% 的缺口**：`user.py` 有 3 行未覆盖（81%），其余 5 个模块均 ≥95%。
> 未直接设 90% 是因为那会让 CI 立刻变红、阻断所有合并——**这不是修问题，是把问题变成路障**。
> 处置：门禁先设 80% 防止继续下滑，90% 作为**评审判据**保留；补测任务见 §4「需补测的模块清单」P0 行。
> 这条**如实记录为未达标**，不按达标处理。

## 5 墙钟抖动处置（E-1）

### 5.1 事实

`backend/tests/unit/core/algorithms/` 下有 **4 处墙钟微基准断言**（200 / 50 / 20 / 100 ms）。
全量套件在 CPU 争用下失败，**单独跑全过**。属既有**测试设计问题**，与具体改动无因果关系。

### 5.2 处置规则（不放宽阈值）

| 场景 | 处理 |
| --- | --- |
| 准出取证 | 用 **§3.3 串行运行**结果作为 QG-1 的通过率证据 |
| 全量并发抖动 | 记为 E-1，**不计为准出阻断项**，但必须进缺陷台账 |
| 复跑确认 | 抖动失败项 `-k` 单独串行复跑，确认通过后附在取证里 |
| **禁止** | ❌ 放宽阈值 ❌ 把抖动当自己引入的回归去追（`AGENTS.md` 定案） |

### 5.3 根治方向（属后续任务）

改为相对基准（如"是否处于同量级"）或标记为性能基准单独跑，**不作为 CI 正确性断言**。
——一个会随机变红的门禁，会让真正的回归淹没在噪音里。

## 6 用例规范

### 6.1 结构与命名

| 项 | 约定 |
| --- | --- |
| 后端位置 | `backend/tests/unit/<层>/test_<模块>.py`（沿用现状目录） |
| 前端位置 | `miniprogram/tests/<主题>.spec.ts`（**平铺，无 `unit/` 子层级**） |
| 用例名 | 被测对象 + 条件 + 期望，例如「未判完时 `loadReport` 返回 `null` 且不发诊断请求」 |
| 结构 | Arrange / Act / Assert 三段；一个用例只断言一个行为 |
| 契约测试 | 后端字段变更时，前端 `fixtures/backendResponses.ts` 同步更新并附后端口径注释 |

### 6.2 断言要求

- **不许"只跑不断言"**：用例必须 `expect/assert` 具体行为，不能只调用函数。
- **不许靠手工补字段让断言通过**：空态/缺失场景应断言真实的 `undefined`/`null`。
- **关键改动做变异验证**（沿用 `docs/开发过程文档.md` §5.3）：
  ≥1 处破坏 → 确认用例失败 → 恢复。**没通过变异验证的用例不算用例**。

### 6.3 反例（写进用例模板的"禁止"）

```python
# ❌ 只执行不断言：覆盖率涨了，行为没锁住
def test_grade():
    grade(answer, rubric)

# ✅ 锁住契约
def test_grade_marks_pending_when_llm_timeout():
    result = grade(answer, rubric)
    assert result.score is None          # 不伪造 0 分
    assert result.status == "pending_regrade"
```
