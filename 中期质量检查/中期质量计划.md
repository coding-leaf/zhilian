## 1 目标与范围

### 1.1 目标

在期中节点，用一次有范围、有标准、有角色、有排期的质量检查，回答三个问题：

1. **主链路是否真的通**——8 节点端到端可走通，而不是"单侧修好了"；
2. **新增与高危代码是否被测试锁住**——不是"跑过覆盖率"，而是断言真的锁住了行为；
3. **遗留问题是否全部有归宿**——已修 / 已决策顺延 / 明确不做，没有"记了但没人管"。

### 1.2 覆盖范围

- **新增代码**：自版本控制收敛起点（提交 `ZL-143`，2026-09-29）以来合入 `master` 的改动。
- **修改频繁模块**：全历史 churn Top20 的文件（客观定义见 §2.5）。
- **核心业务**：主链路 8 节点所经的后端 service / schema / repository / core 与前端网络层、store、主页面。
- **高风险模块**：编译器管不到的三类——算法核、鉴权与用户隔离、错误契约。

### 1.3 不在范围内

沿用 `docs/后续待解决问题.md` §六的既有结论，**不重复判定**：

| 类别 | 内容 |
| --- | --- |
| 永久排除（本期与后续都不做） | 院校教务系统/学籍对接 · 教师端与班级管理 · 实时在线授课组件 · 商业化付费与交易闭环 · 公共社交广场与社区 · 独立多级人工审核后台 |
| 延期到 P1/P2 里程碑 | 复杂公式与图表高精度渲染 · 多模态语音作答与判题 · 第三方题库批量导入导出 · 协作式组队练习与 PK 竞速 · 跨资料全局知识图谱交叉融合 |
| 平台与能力边界（约束，非缺陷） | 仅微信小程序原生端 · 题型仅单选/多选/判断/主观简答 · 单文件 ≤20MB、页数 ≤50 页、单次出题 1~50 题 · 断网不支持生成题目与诊断报告 |

**本任务自身不做**：不修业务缺陷、不改门禁命令、不改既有三份文档。

## 3 准出标准

三层结构。「可判定」= 能写成 **命令 + 期望输出 + 判定人**。

### 3.1 总览

| 编号 | 标准 | 层 | 判据 | 判定人 |
| --- | --- | --- | --- | --- |
| QG-1 | 单元测试通过率 **100%** | L1 | `task verify` 全绿 | CI / Reviewer |
| QG-2 | 增量覆盖率：新增/改动代码 **≥ 80%** | L2 | `diff-cover --fail-under=80` | CI / Reviewer |
| QG-3 | 增量覆盖率：**T0 核心模块 ≥ 90%** | L2 | 对 T0 路径单独 `--fail-under=90` | CI / Reviewer |
| QG-4 | 静态扫描**无阻塞问题** | L1 | ruff/mypy/lint-imports/eslint/vue-tsc 全清 + 安全扫描无 high | CI |
| QG-5 | 代码评审问题**全部闭环** | L3 | 缺陷台账无 open 项 | Reviewer |
| QG-6 | 主链路 8 节点端到端可走通 | L3 | 里程碑验收证据 | Reviewer |

### 3.2 L1 硬门禁（沿用现状，不新增）

| 检查 | 命令 | 判据 |
| --- | --- | --- |
| 后端格式/静态 | `uv run ruff format --check . && uv run ruff check .` | 无告警 |
| 后端类型 | `uv run mypy app` | 严格模式 0 错 |
| 后端架构契约 | `uv run lint-imports` | 5 条契约全过 |
| 后端单测+全量覆盖率 | `uv run pytest tests --cov=app --cov-branch --cov-fail-under=80` | 全绿且 ≥80% |
| 前端静态/类型 | `pnpm run lint && pnpm run type-check` | 0 错 |
| 前端单测 | `pnpm run test:unit` | 全绿 |

**QG-1 的取证与例外规则（针对 E-1 墙钟抖动）**：

- **准出取证运行** = 单进程串行全量：`uv run pytest tests -o addopts="" -p no:cacheprovider`
  （`backend/tests/unit/core/algorithms/` 的 4 处墙钟断言在此形态下全过）。
- 全量**并发**运行的抖动结果不作为准出阻断项，但必须计入缺陷台账（E-1）。
- **不放宽阈值**：遵守 `AGENTS.md` 既有结论——放宽阈值是把测试改到通过，不是修问题。

### 3.3 L2 增量门禁（本期定义，后续实施）

用户口径"新增代码覆盖率 ≥ 70%~80%，核心模块 ≥ 90%"落到可执行形态：

| 项 | 定义 |
| --- | --- |
| 口径 | **增量（diff）覆盖率** = 本次改动的新增/修改行中被用例执行到的比例 |
| 后端工具 | `diff-cover`，输入 `coverage.xml`，基线 `origin/master` |
| 后端命令 | `uv run pytest tests --cov=app --cov-branch --cov-report=xml && uv run diff-cover coverage.xml --compare-branch=origin/master --fail-under=80` |
| T0 加严 | 对 `app/core/algorithms/`、`app/core/security.py`、`app/api/deps/`、`app/core/errors.py` 的改动单独 `--fail-under=90` |
| 前端工具 | **先接入** `@vitest/coverage-v8`（当前缺失），`vitest run --coverage` |
| 前端策略 | 接入后先以 `thresholds: 0` 观察一个里程碑，再设阈值——避免一开始就用错基线 |
| 与全量的关系 | 增量门禁**叠加**在全量 ≥80% 之上，不替换（全量防倒退，增量防"新代码不测"） |

> 为什么不全量提到 90%：全量覆盖被历史代码摊薄，一刀切会逼出为凑数而写的无断言用例。
> 增量口径直接对齐"新增代码必须有测试"这条真实意图。

### 3.4 L3 人工评审

- **双人评审**：T0 模块改动必须双人评审且包含所有权人（`docs/团队分工.md` §4）。
- **闭环**：缺陷台账（按 `templates/缺陷记录表模板.md`）在里程碑收口时**无 open 项**；
  未修项必须写成显式决策（理由 + 影响 + 下一步），不允许"记了但没人管"。
- **质量否决**：Reviewer 对「主链 P0 验收未过」或「阈值改动缺回归证据」可否决，
  只暂停交付、不改需求（`docs/团队分工.md` §5）。

### 3.5 准出判定矩阵（按里程碑）

| 里程碑 | 必过 | 可顺延（须留痕） |
| --- | --- | --- |
| M0 | QG-1 / QG-4 | QG-2 / QG-3（前端工具未接入前） |
