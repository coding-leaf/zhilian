| 项 | 值 |
| --- | --- |
| 文档定位 | 《中期质量计划》§3 准出标准在**本项目具体模块**上的落地检查表 |
| 编制日期 | 2026-10-03 |
| 分级依据 | churn Top20 ∩ 主链路 ∩ 编译器盲区（推导见 `.trellis/tasks/10-03-midterm-quality-prep/research/baseline-and-risk.md`） |

---

## 1 使用说明与放行规则

1. 每次评审一份**改动集**（一个 PR / 一个里程碑批次），按下表逐项打勾。
2. 三项状态：`✔ 通过` / `✘ 打回` / `— 不适用（须写理由）`。
3. **T0 改动**：双人评审且必须含所有权人；任一人打回即打回。
4. **T1 改动**：单人评审（所有权人）。
5. **T2 改动**：抽检。
6. 打回项必须写明：未通过项 + 复现证据 + 期望结果。修复后**重新评审该项**，不整份重来。
7. 评审结论写入缺陷台账（`templates/缺陷记录表模板.md`）；未修项须有显式决策。

## 3 T0 高危模块（双人评审 + 覆盖率 ≥90%）

> **口径更正（2026-10-03 晚）**：T0 的 90% 是**绝对**覆盖率，由
> `coverage report --include=... --fail-under=90` 判定，**不是** diff-cover 的增量口径。
> 原因：diff-cover 的 `--include` 在本项目布局下**永不匹配**，且失败方式是
> 「输出 `No lines with coverage information` 并 exit 0」= **静默放行**——比没有门禁更危险
> （详见《单测计划》§3.1）。
>
> ⚠️ 另需注意：`app/api/deps/` 当前实测 **83%，尚未达到 90%**，CI 门禁暂设 80% 防下滑。
> **评审时按「未达标」对待**，缺口见《单测计划》§4。

### 3.1 后端

| 模块 | 检查项 | 证据要求 | 评审人 |
| --- | --- | --- | --- |

| 同上 | 用户数据隔离 key 是否含用户维度（防跨用户复用） | 代码锚点 + 用例 | SecLead + TechLead |
| `app/core/errors.py` | 上游真实原因是否在接口层被保留（防 P0-2 的"错误原因被丢掉"） | 错误响应契约 + 用例 | TechLead + SecLead |

| `app/repositories/material.py` | 归属字段（`folder_id`/`material_id`）的过滤是否与聚合口径一致（防 P1-4 漏算） | 查询 + 聚合用例 | SecLead + Reviewer |

## 6 三类编译器盲区 · 专项（T0 必查）

> 这三类错误的共同点：**编译器不会发现**，只会让判分/授权悄悄出错。来自 `docs/团队分工.md` §4。

| 盲区 | 专项检查项 | 通过判据 |
| --- | --- | --- |
| **① 算法核** | 每个纯函数模块有边界用例；改阈值附依据；分支覆盖率 100% | 用例全过 + 覆盖率报告 |
| **② 鉴权与用户隔离** | 每个受保护资源有"他人访问被拒"负向用例；隔离 key 含用户维度 | 负向用例全过 |
| **③ 错误契约** | 上游错误原因不被丢弃；错误码 ↔ HTTP 状态唯一映射 | 契约用例全过 |

## 7 放行 / 打回判定

```
通过（可合并）  : T0 双人 + T1 单人 + 通用项全 ✔ + 增量覆盖率 ≥80% + T0 绝对覆盖率 ≥90%
打回（须修）    : 任一 T0 打回 / 通用项 ✘ / 覆盖率未达 / 缺回归证据
不适用（须理由）: 该项与本改动无关，且理由写进评审记录
```

- **质量否决**（Reviewer）：主链 P0 验收未过，或阈值改动缺回归证据 → 暂停交付，不改需求。
- **升级路径**：当事人协商 → TechLead 裁决 → 质量否决 → 指导教师评审（`docs/团队分工.md` §5）。
- 评审记录与打回项统一进缺陷台账；**未修项须有显式决策**，不接受"记了但没人管"。
