## 1 共性问题与根因

### 1.1 测试代码问题（共 7 类）

#### 问题 1：测试锁住了 bug 行为（🔴 阻塞，PR2-01）

**现象**：
```python
def test_attempt_item_id_with_detail_alias_kwargs(self) -> None:
    err = AttemptItemNotFoundError(
        message="明细缺失",
        detail={"context": "retry"},
        attempt_item_id="item-1",
    )
    assert err.details["context"] == "retry"
    # 当前实现下 attempt_item_id 注入会被 detail 别名覆盖（已知行为，需后续评审）
```

**根因**：
- 测试**主动**断言了「`detail` 别名覆盖 `attempt_item_id` 注入」这一**错误行为**
- 没有把「测试应锁住正确行为」作为基础原则
- 测试编写者害怕「修复产品代码会破坏测试」，反向让测试适配 bug

**改进措施**：
- ✅ 写测试时只锁住「正确行为」契约，不锁住「当前行为」
- ✅ 发现 bug 时**修复产品代码**，而非「标记已知 bug」
- ✅ 用 `pytest.xfail` + 缺陷单替代「测试锁住 bug 行为」

---

#### 问题 2：mock 桩与产品代码状态机脱节（🔴 阻塞，PR3-01）

**现象**：
```python
class _StubSession(Session):
    def __init__(self) -> None:
        # 跳过父类 __init__ 的实际绑定逻辑
        self._closed = False
    def close(self) -> None:
        self._closed = True
```

**根因**：
- 自定义 stub 跳过 `Session.__init__`，**未走 SQLAlchemy 内部状态机**
- `close()` 仅设标志位，与真实 Session 关闭机制不同
- 测试断言依赖 `_closed` 内部字段，**未来 SQLAlchemy 升级会瞬间崩溃**

**改进措施**：
- ✅ 用 `MagicMock(spec=Class)` 替代自定义 stub
  - `spec` 自动跟随被测类接口变更
  - `isinstance(m, Session)` 自动满足
  - `m.close.assert_not_called()` 严格验证方法调用
- ✅ 仅在「桩需要复杂行为」时才自定义

---

#### 问题 3：异常捕获过于宽（🟠 重要，PR4-02）

**现象**：
```python
try:
    ...
    task_id = self.queue.enqueue(...)
    self.session.commit()
except Exception:
    # 入队失败必须回滚状态
    self.session.rollback()
    raise
```

**根因**：
- 「宽捕获」是开发者**偷懒**的常见反模式
- 会吞掉 `KeyboardInterrupt`、`SystemExit` 等非业务异常
- 掩盖了「实际根本不该捕获」的异常
- 与「**让错误暴露**」的最佳实践相悖

**改进措施**：
- ✅ 必须捕获**具体异常类型**：`except (QueueError, SQLAlchemyError):`
- ✅ 用 `pytest.raises(SpecificException)` 而非 `pytest.raises(Exception)`
- ✅ 「不捕获」优于「宽捕获」

---

#### 问题 4：mock 断言依赖内部状态（🟠 重要，PR3-03）

**现象**：
```python
assert injected_session._closed is False  # 内部私有字段
```

**根因**：
- `_closed` 是 stub 实现细节，**不是契约**
- 真实 Session 用 `_close_impl` 等内部协议
- 依赖私有字段 = 隐性耦合 = 升级敏感

**改进措施**：
- ✅ 断言「**方法调用次数**」：`close.assert_not_called()` / `assert_called_once()`
- ✅ 断言「**返回值**」而非「**内部表示**」

---

#### 问题 5：迭代器隐式 StopIteration（🟠 重要，PR3-04）

**现象**：
```python
self._marker_cycle = iter(["marker-A", "marker-B", "marker-C"])
# 第 4 次 next() 会抛 StopIteration
```

**根因**：
- `iter([...])` 在第 N+1 次调用时**隐式失败**
- 测试难以预测何时会抛错
- 真实生产中「计数器用尽」可能是正常场景

**改进措施**：
- ✅ 用 `itertools.cycle(...)` 表达「无限循环」
- ✅ 用 `itertools.count()` 表达「无限计数」
- ✅ 永远不要假设 list 长度足以覆盖所有场景

---

#### 问题 6：评审清单措辞与产品无关（🔴 阻塞，PR2-02）

**现象**：
```python
"""上游异常原因保留契约：防 P0-2「思考模式模型上结构化输出不可用」中的错误原因丢失。"""
```

**根因**：
- docstring 引用了与错误契约**无关**的模型术语
- 评审发现这是「**外部上下文侵入**」的痕迹
- 测试代码应在被测代码的语义边界内描述

**改进措施**：
- ✅ docstring 描述应**完全聚焦于被测对象的契约**
- ✅ 关联需求/缺陷时用编号（如 `P0-2`），不用完整描述
- ✅ 评审「**文档关联性**」检查项

---

#### 问题 7：回归保护缺失（PR1-04）

**现象**：
- `archived=True` 课程资料被移动的用例缺失
- 缺跨用户同 `idempotency_key` 场景测试

**根因**：
- 测试编写时**只覆盖主路径**
- 边界用例（archive 状态、跨用户）未在测试设计中明确
- 没有「**等价类划分清单**」的强制约束

**改进措施**：
- ✅ 编写测试前先列「**等价类划分 + 边界值清单**」
- ✅ 主路径 + 边界 + 异常三类用例必须有明确对应
- ✅ 评审时检查「**等价类覆盖矩阵**」是否完整

### 1.2 产品代码问题（共 3 类）

#### 问题 8：错误类 `detail` 别名覆盖参数注入（BUG-01）

**现象**：
```python
merged_details = dict(detail or details or {})
if attempt_item_id is not None:
    merged_details["attempt_item_id"] = str(attempt_item_id)
super().__init__(
    error_code=error_code,
    message=message,
    status_code=status_code,
    details=merged_details,
    code=code,
    detail=detail,  # ← BUG：detail 别名优先，merged_details 被覆盖
)
```

**根因**：
- 父类 `AppError.__init__` 优先用 `detail` 别名（`actual_details = detail if detail is not None else (details or {})`）
- 子类合并 `merged_details` 后**同时**传给父类
- 父类用 `detail` 别名**反向覆盖**了合并结果
- 3 个错误类（AttemptItemNotFoundError / MasteryRecordNotFoundError / WrongRecordNotFoundError）**同源 bug**

**改进措施**：
- ✅ **通道分离**：子类构造 `details` 后**只传 details**，不传 `detail` 别名
- ✅ **协议优先**：子类继承父类时**不要重新引入父类已废弃的别名**
- ✅ **全量修复**：同类模式（`merged_X + super().__init__(X_alias, ...)`）必须一并扫描修复

---

#### 问题 9：状态跃迁后实体消失未回滚（BUG-02）

**现象**：
```python
try:
    transitioned = self.practice_repo.try_transition_status(...)
    task_id = self.queue.enqueue(...)
    self.session.commit()  # ← 状态已提交到 SUBMITTED
except (QueueError, SQLAlchemyError):
    self.session.rollback()
    raise

# 注意：此处不再受 try 保护
practice = self.practice_repo.get_practice_by_id(...)
if practice is None:
    raise PracticeNotFoundError(...)  # ← 抛错无 rollback，状态永久卡住
```

**根因**：
- 事务逻辑**部分**进入 try 块
- 二次校验（get_practice_by_id）**在 try 块外**
- 并发删除时，状态已 commit + 二次校验抛错 + 无 rollback = **永久泄漏**
- 这类「**部分事务**」是难以察觉的状态泄漏根源

**改进措施**：
- ✅ 二次校验也**纳入 try 块**或**重做事务**
- ✅ 用 SELECT FOR UPDATE 锁行避免并发删除
- ✅ 「**事务边界**」必须经过评审 / 单测锁定

---

#### 问题 10：`except Exception` 太宽（BUG-03）

**现象**：
```python
except Exception:  # ← 捕获 KeyboardInterrupt / SystemExit
    self.session.rollback()
    raise
```

**根因**：
- 「**捕获所有异常**」是常见的错误习惯
- 实际上应该捕获**具体的业务异常**
- 异常处理边界模糊化 = 测试与生产均无法准确识别问题

**改进措施**：
- ✅ 必须捕获**具体异常类型**（`QueueError, SQLAlchemyError`）
- ✅ 用 `Exception` 捕获时必须**有显式注释**说明捕获范围
- ✅ 评审「**异常捕获类型**」检查项

## 2 优秀实践（共 6 项）

### 2.1 用 parametrize 表达等价类（PR2-03）

**实践**：14 → 41 项错误码 ↔ 状态码映射 parametrize。

```python
@pytest.mark.parametrize(
    ("error_class", "expected_code", "expected_status"),
    [
        (AuthenticationError, 20001, 401),
        (PermissionDeniedError, 20002, 403),
        ...  # 41 项
    ],
)
```

**价值**：
- 等价类划分显式表达
- 新增错误类只需追加一行
- pytest 报告**精确到每个等价类**

### 2.3 `MagicMock(spec=Class)` 替代自定义 stub

**实践**：删除 `_StubSession(Session)`，改用 `MagicMock(spec=Session)`。

```python
# 之前（反模式）
class _StubSession(Session):
    def __init__(self):
        self._closed = False
    def close(self):
        self._closed = True

# 之后（最佳实践）
injected_session = MagicMock(spec=Session)
injected_session.close.assert_not_called()
```

**价值**：
- spec 跟随 SQLAlchemy 接口变更
- 断言验证**方法调用**而非**内部状态**
- pytest 标准用法

### 2.4 `itertools.cycle` 替代 `iter([...])`

**实践**：
```python
self._marker_cycle = itertools.cycle(["marker-A", "marker-B", "marker-C"])
```

**价值**：
- 永远不会 StopIteration
- 表达「**循环迭代**」语义更清晰
