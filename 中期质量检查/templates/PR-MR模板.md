# PR / MR 模板

> 用途：发起合并请求时按此填写。合并请求描述直接粘贴本模板正文。
> 依据：`docs/开发过程文档.md` §6.2（分支名与提交 scope 向《代码管理工作介绍 V1.0》收敛）。

---

## 标题格式

```
<类型>/<任务编号>-<短描述>          ← 分支名
<类型>(<scope>): <一句话说明>       ← 提交信息
```

- **类型**：`feature` / `fix` / `docs` / `chore` / `refactor` / `test` / `ci`
- **scope 词表**（只取以下值）：`api` / `services` / `algorithms` / `integrations` /
  `models` / `miniprogram` / `deploy` / `ci` / `docs`
- **分支名**：`类型/任务编号-短描述`，如 `feature/ZL-150-midterm-quality-prep`
- **合并方式**：保留**合并提交**（使分支结构在 `git log --graph` 中可见），不用 squash

---

## 描述模板

```markdown
## 关联

- 任务：`<Trellis 任务目录>` / `<ZL 编号>`
- 关联缺陷：`<P0-x / P1-x / 无>`
- 依赖 / 被依赖：#<PR 编号>

## 改了什么

- <按模块列出改动，一句话一条>

## 为什么

<根因或需求背景；如果是修复，写清"静默失效"还是"显式报错">

## 怎么验证

| 项 | 命令 | 结果 |
| --- | --- | --- |
| 后端门禁 | `task verify-backend` | 退出码 <x>，覆盖率 <x>% |
| 前端门禁 | `task verify-frontend` | 全绿 |
| 增量覆盖率 | `uv run diff-cover coverage.xml --compare-branch=origin/master --fail-under=80` | <x>%（T0 <x>%） |
| 新增/修改用例 | <文件> | <n> 条，全过 |
| 变异验证 | 破坏 <x> → 用例 <y> 失败 → 恢复 | ✔ |

## 影响面 / 风险

- 契约变更：<有/无；有则列出前后端同批改动>
- 迁移：<有/无；有则附降级验证>
- 回滚：<如何回滚；文档类改动 = 删除新增文件>

## 评审要点

- [ ] T0 模块已双人评审（含所有权人）
- [ ] 增量覆盖率达标（T0 ≥90%，其余 ≥80%）
- [ ] 阈值/参数类改动附回归证据
- [ ] 无真实姓名（仓库公开）
- [ ] 文档与代码同批（接口变更已更新对应章节）

## Checklist

- [ ] 分支名符合 `类型/任务编号-短描述`
- [ ] 提交 scope 在词表内
- [ ] `task verify` 退出码 0，且**逐段输出**无错误（防退出码假失败）
- [ ] 新增/改动代码有测试锁住（做过变异验证）
- [ ] 无静默吞错
```

---

## 评审与合并规则

| 改动级别 | 评审要求 |
| --- | --- |
| T0 模块 | **双人评审**，必须含所有权人；任一人打回即打回 |
| T1 模块 | 单人评审（所有权人） |
| T2 模块 | 抽检 |

- 作者**不能自评自合** T0 改动（`docs/团队分工.md` §4）。
- 合入前必须在 GitHub Actions 上**实际跑绿**（不以本地模拟为准）。
- 打回项修复后**只重评审该项**，不整份重来。

## 禁止

- ❌ 同一个 PR 混入无关改动（一 PR 一个连贯改动单元）
- ❌ 直接推 `master`（分支保护会拒绝）
- ❌ squash 合并（会抹掉分支结构证据）
- ❌ 在提交信息 / 分支名 / 文档里出现真实姓名
