## 2 开发方法：任务树驱动

项目没有用「想到哪改到哪」的方式推进，全部改动都挂在任务上。前后用过两套任务体系：

### 2.1 前期：原子任务矩阵（ZL 编号）

`docs/legacy_sdlc/ROADMAP.md` 把 P0 范围解构成 **35 个聚焦单一关注点的原子任务**
（ZL-103 ~ ZL-137），并画出依赖 DAG。切分原则写在文件开头：

> 纯函数计算核先行、仓储与适配解耦、服务层统领事务、前端组件小步快跑、端到端物理闭环验收。

每个任务有 `intent.md` / `plan.md` / `spec.md` 三份产物。**40 个任务已归档**，
台账在 `docs/legacy_sdlc/ARCHIVE.md`，每条记录都带验证证据（测试数、覆盖率、契约违规数）。

架构分层刻意按「最容易被错误污染」的优先级排序：

| 阶段 | 内容 | 为什么先做 |
| --- | --- | --- |
| S1 数据模型 | 用户、资料、知识点、题目、练习、掌握度 | 后面所有层都依赖它 |
| S2 纯函数算法核 | 分块 / 质检 / 判题 / 掌握度 / 诊断 | **纯函数可以被穷举测试**，先做才能把最贵的错误挡在早期 |
| S3 外部适配 | 存储 / OCR / 向量 / 大模型 / 队列 | 全部收敛到协议抽象后，测试不再依赖外部服务 |
| S4 业务编排 | 服务层统领事务 | 事务边界只在一层，避免跨层提交 |
| S5 前端 | 组件与页面 | 接口契约稳定后再做，减少返工 |

### 2.2 后期：Trellis 任务树

引入 `.trellis/` 后，任务改为「父任务持有需求源与跨子任务验收标准，子任务可独立验证、独立归档」。
每个任务落 `prd.md`（需求与验收）、`design.md`（技术设计）、`implement.md`（执行清单）。

规矩是：**任务创建批准不等于实现批准**。规划产物先审，审过才 `start` 进入实现。
这条规矩挡掉过至少一次错误开工——见 3.2 节「先证伪再动手」。

### 2.3 开发日志

`.trellis/workspace/coding-leaf/journal-1.md` 按会话记录 **13 次开发**，每次写清：
做了什么、动了哪些文件、提交了什么、测试结果、当前状态（`[DONE]` / `[PARTIAL]` / `[BLOCKED]`）。
日志里 `[PARTIAL]` 是常态——**不把没做完的写成做完了**。

## 3 关键决策

### 3.1 把文档矛盾当阻塞项处理

规划阶段对《软件需求规格说明书 V2.0》与《概要设计说明书 V1.0》做交叉审查，识别出 **3 处深层冲突**，
全部写进 `docs/legacy_sdlc/LEADER_ALIGNMENT.md` 并给出推荐决策，而不是含糊带过。典型的一处：

**判题超时降级的因果倒置**。概要设计同时写了三句话——「待重新判题按 0.5 权重参与计算」、
「参与计算的记录限定为最近 200 条有效记录，待重新判题的记录不参与计算」、
「全部记录都是待重新判题时返回 0 与未学档次」。三句话互相矛盾。

危险不在于矛盾本身，而在于**因果倒置**：若在存在「待重新判题」时立刻算掌握度并生成报告，
该知识点极可能被误判为「薄弱」并被推荐继续练习——**用户会因为系统判不出来而被判定为没学会**。

### 3.2 先证伪再动手

一次实测反馈：「我在已有解析资料的资料上试着生题，但是没有反馈，也不知道题目在哪里」。
第一反应是归因于解析链路。规划阶段拿证据推翻了这个假设：

- 用户用的是**已解析就绪**的资料，现象与解析无关；
- 真因在 `questions/index.vue`：`isConfigMode` **没有任何一处被写成 `false`**，
  于是预览区（生成的题目、覆盖缺口、「开始作答」按钮）是**不可达的死代码**。

同一批里还有一条：用户说「选择题也要判题，不该秒出么」。真因不是「客观题判得慢」，
而是**所有判题都异步入队**，而 worker 在本机不可用，于是全部停在「判题中」。

**这两条修正本身是规划的产出**。父任务在收口时被明确要求**重新核对**这些归因，
而不是在收口时临时扩范围——因为「这是下游后果」是最容易被当成借口、也最容易错的一类判断。

### 3.3 回滚也是过程的一部分

`docs/legacy_sdlc/ARCHIVE.md` 里 ZL-142 记录为：

> 尝试改造登录鉴权、资料卡片重试与 LangGraph Tool Calling，因改动耦合导致前端运行时异常
> **已安全回退**……放弃 `76a7b07`，安全回滚至 `02bf56b` 稳定基线。

这条被**保留在交付台账里**，而不是抹掉。一次有边界的失败回滚，比一次勉强合并的改动更有价值。

## 4 缺陷修复史

挑选修过的缺陷时，优先看**静默失效**那一类：崩溃会给你堆栈，静默只会让数据慢慢变错。

### 4.1 判题结果被全部丢弃

| 项 | 内容 |
| --- | --- |
| 现象 | 交卷后所有题永远停在「判题中」 |
| 根因 | 判题写库后**缺一次事务提交**，判题跑完等于没跑 |
| 修复 | `800c475` fix(grading): 判题结果补上事务提交 |
| 为什么危险 | 没有异常、没有报错，日志里判题「成功」，只有数据库里什么都没有 |

这一条还带出一个过程教训：`7f45062` 与 `9795c60` 两次收口记录分别在纠正
「**足迹存在 ≠ 已修好**」——验收要看端到端结果，不能看中间证据。

### 4.2 无归属 upsert 静默清除归属

| 项 | 内容 |
| --- | --- |
| 现象 | 手动标记错题会把「这道题来自哪次练习」静默抹成 NULL |
| 根因 | `upsert_wrong_record` **无条件覆盖**，手工路径传 `None` 就覆盖掉了判题写下的归属 |
| 修复 | `7ceef10` 改为「非 None 才覆盖」，先写回归测试确认失败再改 |
| 为什么危险 | 错题与练习的追溯链断了，而界面上看不出任何异常 |

### 4.3 浮层吞掉用户输入

| 项 | 内容 |
| --- | --- |
| 现象 | 点输入框浮层就关闭，工作台新建课程、AI 助教抽屉、资料页助教、个人中心四处输入框全部不可用 |
| 根因 | 浮层点击热区与输入区重叠 |
| 修复 | `fb9788a` 把热区**独立成元素** |
| 过程中的弯路 | 曾按几何偏移推断出「backdrop 需要负偏移」，`a4ce6ec` 推翻了这个被写反的结论 |

### 4.4 Windows 上后台任务无人消费

| 项 | 内容 |
| --- | --- |
| 现象 | 上传后永久停在「正在抽取考点拓扑」，无按钮、无提示、无失败 |
| 根因 | RQ 有两处 POSIX-only 依赖：`os.wait4`（`6c3ffcd` 改用 `SimpleWorker`）、`signal.SIGALRM`（`6b9832c` 改用 `TimerDeathPenalty`） |
| 为什么值得记 | 开发环境与部署环境不同，**同一份代码在一处能跑、在另一处静默不工作** |

### 4.5 思考模型上结构化输出全挂

| 项 | 内容 |
| --- | --- |
| 现象 | 换用 DeepSeek 官方 API 后，所有出题 / 抽取调用返回 502，底层是 400 |
| 根因 | 强制 `tool_choice` 与思考模式（thinking mode）不兼容 |
| 修复 | `d0e759b` 不再强制 `tool_choice` |

### 4.6 门禁自己会假失败

| 项 | 内容 |
| --- | --- |
| 现象 | `verify-backend` 在 Windows 上失败，但契约其实一条都没评估 |
| 根因 | `lint-imports` 用 rich 写转圈动画，Windows 控制台默认 GBK，遇特殊字符抛 `UnicodeEncodeError`，**发生在任何契约被评估之前** |
| 修复 | `c47b4b5` 强制 `PYTHONIOENCODING=utf-8`；`AGENTS.md` 同步写明**禁止绕道 WSL** |

这条催生了本项目的质量纪律之一（记录在 `61c1de1`）：**退出码与覆盖率都会骗人**。
退出码 1 背后可能没有结论；覆盖率数字可能被排除清单抬高。两者都不能单独当作证据。

## 5 质量证据

### 5.1 门禁

`task verify` 一条命令跑完七道：

| 层 | 检查 | 阈值 |
| --- | --- | --- |
| 后端 | `ruff format --check` / `ruff check` | 无告警 |
| 后端 | `mypy app`（严格模式） | 无错误 |
| 后端 | `lint-imports` | 5 条架构契约全部通过 |
| 后端 | `pytest` | 覆盖率 ≥ 80%（实际 91%+） |
| 前端 | `eslint` / `vue-tsc` | 无错误 |
| 前端 | `vitest` | 全部通过 |

同一套门禁已接进 GitHub Actions（`.github/workflows/verify.yml`），push 与 PR 都会跑。

### 5.2 测试规模与形态

| 项 | 数值 |
| --- | --- |
| 后端测试文件 / 函数 | 91 / 548 |
| 前端测试文件 / 用例 | 13 / 125 |
| 算法核模块 | 9 个纯函数模块，分支覆盖率 100% |

**关键设计**：外部能力全部走协议抽象 + 纯内存假实现，因此全量测试**不依赖数据库与网络**，
秒级跑完。测试慢是覆盖率下滑的第一原因，把依赖摘掉是维持覆盖率最有效的手段。

### 5.3 变异验证

覆盖率会骗人——用例执行过一行代码，不等于断言真的锁住了行为。因此对关键改动做
「故意破坏 → 确认用例失败 → 恢复」的验证。实际做过的几例：

| 破坏动作 | 结果 |
| --- | --- |
| 删掉 `question_count` 传递 | 2 个用例失败 |
| 删掉在途守卫 | 1 个用例失败 |
| 页码改回长度推导 | 1 个用例失败 |
| 把路由挪到 `/{id}` 之后 | 接口返回 422 |

**没通过变异验证的用例不算用例**，尤其对算法核与鉴权这类编译器管不到的错误。
`7495c60` 那条记录「足迹存在 ≠ 已修好」也是同一个道理。

### 5.4 已知的测试设计问题（未修，如实记录）

`backend/tests/unit/core/algorithms/` 下有 **4 处墙钟微基准断言**（200 / 50 / 20 / 100 ms）。
全量套件在 CPU 争用下会失败，**单独跑全过**。这是既有的测试设计问题，与具体改动无关。

处理方式已写进 `AGENTS.md`：**不放宽阈值、不把它当回归去追**。
放宽阈值是把测试改到通过，不是修问题——而一个会随机变红的门禁，会让真正的回归淹没在噪音里。

## 6 版本控制

### 6.1 分支与提交

《代码管理工作介绍 V1.0》第 3 章定义了精简 Git Flow（main / develop / feature / release / hotfix），
并给出分支命名与提交信息格式。**本仓库的实际执行与文档存在偏差，如实记录如下。**

| 项 | 文档要求 | 本仓库实际 |
| --- | --- | --- |
| 集成分支 | `main` + `develop` 双长期分支 | 单 `master` |
| 短期分支 | `feature/*`、`release/*`、`hotfix/*` | 用过 `feat/*`、`codex/*` 等命名 |
| 分支命名 | `类型/任务编号-短描述` | 历史分支未带任务编号 |
| 合并方式 | feature→develop 压缩合并；release/hotfix→main 普通合并 | 历史提交为线性，**无合并提交** |
| 分支保护 | 受保护分支禁止直接推送、必需检查项全绿 | 收尾前**未配置**；现已在 `master` 上启用 |
| 评审 | 高风险路径双人评审 | 单账号仓库，**「必需评审人批准」不可执行**，见下 |

**为什么是单账号**：本项目在 GitHub 上目前只有一个协作账号。GitHub **不允许 PR 作者批准自己的 PR**，
所以若启用「必需评审人批准」，本仓库的 PR 将永远无法满足条件——等于把 `master` 锁死。
因此 `master` 的保护规则为「必需状态检查 + 禁止直接推送 + 禁止强推 + 禁止删除」，
**不启用必需评审**。评审要求作为**组织层约定**由团队内部执行（见 `docs/团队分工.md`），
不在仓库服务端强制。这一点不隐瞒：它不是「做到了」，而是「当前形态下不可执行」。

### 6.2 收敛起点

**自 2026-09-29（提交 `ZL-143` 起）**，新增工作按文档规范执行：

- 分支名使用 `类型/任务编号-短描述`（如 `feature/ZL-143-lab3-delivery`）；
- 提交 scope 只取文档词表内的值（`api` / `services` / `algorithms` / `integrations` /
  `models` / `miniprogram` / `deploy` / `ci` / `docs`）；
- 非平凡改动走分支 + 合并请求，合并保留**合并提交**，使分支结构在 `git log --graph` 中可见。

历史分支**不追溯改名**——改写已公开历史的风险大于收益。因此上表里的偏差是
**有起点的历史**，而不是持续的违规。

### 6.3 公开仓库的隐私处理

本仓库公开，因此**不记载成员姓名**。分工的**结构与问责关系**进仓库（`docs/团队分工.md`，
角色代号版），姓名留在仓库之外的团队分工提交稿中。仓库内所有提交、评审与所有权讨论
一律使用四个角色代号。

## 7 协作机制

- **任务看板是唯一任务来源**。卡片字段含标题、阶段、责任人、验收判据、状态与关联提交。
  卡片进入「待验证」时，验证人不能是实现人本人。
- **文档与代码同批合并**。接口变更在同一合并请求内更新对应章节，不设「发布前集中补文档」。
- **决策留痕**。超出既有权责的决策写进决策记录，一次一个文件；口头结论不作为依据。
- **阶段收口会**产出验收记录，含完成项、未完成项、顺延项与理由。顺延项最多一项。

## 8 这一版没做完的事

如实列出，完整版见《后续待解决问题》：

1. **4 个 P0/P1 功能缺陷未开工**：解析可能卡死、出题无反馈、思考模型结构化输出不可用、
   学习足迹统计口径漏算。均已定位根因，未实现。
2. **题库 Tab 的信息架构重定义暂缓**：两个子任务已交付（批次分组题库、手动标记错题），
   父任务自身（删 summary 卡、区块重排、tabBar 改名、空态三档）未做。
3. **一处会误导用户的功能缺陷**：举一反三按「全部生成题目」算覆盖率，而练习按 `question_count`
   只收前 10 题，故界面可能声称某考点已覆盖、而对应题目根本没进练习。
4. **4 处墙钟微基准**在全量套件下抖动（见 5.4），未修。
5. **测试与文档的偏差**：上表所述的分支模型偏差不会追溯修正，只从 ZL-143 起收敛。
