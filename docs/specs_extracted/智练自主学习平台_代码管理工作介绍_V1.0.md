# 1 引言

本章交代这份文档要解决什么问题、约束哪些人与哪些目录，以及它与课程 AI 实践演练之间的关系。读者读完本章应当能判断：一次代码提交是否落在本文档的约束范围内，遇到文档未覆盖的情况又应当按什么流程申请例外。

## 1.1 编写目的

本文档定义智练项目在代码规范、源代码管理、测试工具、持续集成与缺陷跟踪五个方面的具体约定，供四名项目组成员在日常开发、提交与评审时直接执行。课程任务要求提交代码管理工作介绍，并对代码规范、源代码管理工具、测试工具三项有明确指向，本文档第 2 章至第 4 章分别对应这三项，第 5 章至第 7 章补充支撑这三项的流水线、缺陷与协作约定。
文档面向四类读者。开发人员按第 2 章与第 3 章的要求编写并提交代码；测试人员按第 4 章执行测试并依据第 6 章记录缺陷；负责部署的成员按第 5 章维护流水线与部署脚本；指导教师与验收人从第 3 章至第 7 章判断项目的工程管理水平。
本文档不承担三项职责。它不定义产品功能，功能需求的唯一来源是软件需求规格说明书。它不写接口字段级明细，接口定义由 Pydantic v2 模型与 FastAPI 在运行时自动生成 OpenAPI 文档。它不覆盖本期明确不做的范围，包括院校教务对接、班级管理、在线授课、支付结算、公开社区与内容审核后台。

## 1.2 适用范围

本文档适用于 zhilian 仓库的全部受版本控制内容，包括后端服务、小程序端、部署配置、工程脚本与项目文档。约束对象是项目组四名成员在本项目上产生的全部提交，不区分提交来自本机编辑器还是协作工具。约束时间从仓库初始化开始，到课程交付验收结束。
强制级别沿用项目统一用词。写"必须"的条目属于强制要求，不满足即视为对应环节验收不通过；写"应当"的条目属于推荐要求，偏离时需要在合并请求中记录理由、影响与补偿措施；写"可以"的条目属于可选能力，不实现不影响验收。本文档出现的阈值都是可直接执行判定的数值，不使用"较快""合理""较高"这一类无法验收的描述。
本文档与其它文档冲突时按以下顺序取用。产品功能与范围以软件需求规格说明书为准；算法与模块边界以概要设计说明书为准；代码流程与工具阈值以本文档为准；人员归属同时以本文档第 3.6 节与团队分工文档为准。四份文档之间的表述不一致时，提交到每周同步会由技术负责人裁定，裁定结论应当回写到本文档的修订记录中。

## 1.3 与 AI 实践演练的关系

本项目的工程规范并非全部从零拟定。分支策略、提交信息格式、评审要点分级、质量门禁阈值思路与缺陷生命周期这几块，来自学习通 AI 实践课程《软件工程全链路实战：从需求到发布的团队协作演练》的七个里程碑。该演练已经完成并留有作答记录，两轮作答都跑完七个节点，成绩记录见附录 A。
演练抽取的场景是校园二手交易平台，使用另一套服务端技术栈与另一套任务看板工具，与本项目的 Python 技术栈和微信小程序形态没有对应关系。本文档只吸收演练中的流程约定与判断标准，不吸收演练的业务内容，也不照搬演练的技术选型。演练中要求提交单元测试、代码评审意见、缺陷报告与持续集成配置这几件事本身是通用的工程动作，落到智练项目上就换成本项目的工具链与目录结构。
附录 A 完整记录七个里程碑的交付要求、解锁条件、与本项目各交付物的映射关系以及两轮作答成绩。第 3 章至第 6 章的若干条约定会在正文中标注其来源，便于验收人核对哪些做法是课程演练的直接产物。

# 2 代码规范

代码规范处理的是四个人在同一个仓库里写代码时最容易产生摩擦的部分：文件放在哪里、名字怎么起、模块之间能不能互相引用、出错和记日志按什么格式。本章条目以可被工具检查为前提，能用 Ruff、mypy 或脚本判定的规则写成硬约束，只能靠人判断的规则写进第 3.4 节的评审要点。

## 2.1 仓库结构与目录约定

仓库采用单一仓库管理后端、小程序端、部署与文档，避免四份交付物与实现代码分散到多个地址后失去对应关系。目录划分按运行单元组织，每个顶层目录都有唯一职责。
目录约定有六条。运行时代码只允许出现在 backend/app 与 miniprogram/src 下，工程脚本放 tooling，文档放 docs。测试代码与被测代码同仓但不同目录，禁止把测试放在 backend/app 内。生成物、虚拟环境、依赖缓存与构建产物一律不进仓库，由 .gitignore 兜住，前端产物在流水线中以构建产物形式归档。样例资料放 backend/tests/fixtures 且单个文件不超过 200 KB，真实用户资料不得进入仓库。新增顶层目录必须先经技术负责人同意，并在同一次提交中更新本节目录树。文档与代码同仓管理，文档改动的评审要求与代码一致，见第 7.3 节。

## 2.2 命名规范

命名的目标只有一个：任何成员在搜索框里输入一个业务词，能在一分钟内定位到相关模块、数据表、接口与组件。同一业务概念在各层应当保持可对应，例如资料在数据库表中写作 materials，在接口路径中写作 /materials，在前端状态里写作 materialStore。各类对象的规则与正反示例见表 2-1。

## 2.3 分层与依赖方向

后端按职责分为五层，依赖方向单向向下，禁止反向引用与跨层跳跃。这条约束的直接收益是算法与业务编排可以脱离数据库和网络单独测试，测试速度与稳定性都由它决定。
路由层位于 app/api/v1，只做三件事：解析请求、调用 Pydantic 模型校验入参、把服务层返回值转成响应模型。路由函数体内不得出现数据库会话操作、外部服务调用与超过一行的业务判断。服务层位于 app/services，负责事务边界、多步骤编排与外部能力组合，是唯一允许开启数据库事务的层。仓储层位于 app/repositories，封装针对数据表的查询与写入，所有涉及用户数据的查询必须带上用户条件。算法层位于 app/core/algorithms，只包含纯函数，输入输出都是普通数据结构。外部能力适配层位于 app/integrations，用 Protocol 定义接口，具体实现按服务供应商替换。
依赖规则的具体条目如下。app/core/algorithms 下的任何模块不得导入 fastapi、sqlalchemy、httpx、redis、boto3，也不得导入 app/services 与 app/repositories。app/api 不得直接导入 app/repositories，必须经过服务层。app/repositories 不得导入 fastapi，也不得导入 app/integrations。app/integrations 不得导入 app/services。app/core 中的配置、异常与日志模块可被任意层导入，但它们自身不得导入上层模块。
规则的执行靠脚本而非人的自觉。tooling/check_layers.py 解析每个模块的导入语句并与允许矩阵比对，违反时输出文件、行号与违反的规则编号，并以非零状态退出。本地用下面的命令自查，流水线在同一阶段调用同一脚本，因此本地通过即流水线通过。
``bash python tooling/check_layers.py --root backend/app ``
需要临时违反依赖方向时，唯一合法做法是在同一次提交中修改依赖矩阵并在合并请求中说明理由，由技术负责人批准。绕过检查的做法包括在函数内部延迟导入、通过 getattr 动态取模块，这两种写法在评审中直接按阻断级问题处理。

## 2.4 注释与文档字符串

注释解释代码为什么这样写。代码本身已经说明写了什么，重复描述代码的注释在评审中按次要建议处理并要求删除。有四类位置必须写注释：算法中的每一个阈值常量，注明取值来源是决策基线条目、实验数据还是外部接口限制；非显然的边界处理，例如分块时对超长单段的强制截断；为绕开外部服务缺陷而做的特殊处理，注明触发条件与可移除的前提；时间与单位容易混淆的地方，明确写出单位。
有三类位置不写注释：函数名已经完整表达的简单逻辑；被 Ruff 与 mypy 强制保证的类型与格式说明；临时调试留下的标记。被注释掉的代码一律删除，需要保留的历史版本由 Git 承担，不靠注释保留。
公开函数、类与模块必须写文档字符串，采用 Google 风格，至少包含一句话职责说明、参数与返回值，函数有副作用时单独一段说明。算法函数的文档字符串还必须写明前置条件与失败时的返回约定。下面给出一个符合要求的最小示例。
```python def split_material_into_snippets( paragraphs: list[str], max_chars: int = 800, overlap_chars: int = 120, ) -> list[Snippet]: """把解析后的段落序列切分为可检索的知识片段。
Args: paragraphs: 按原文顺序排列的段落文本，调用方保证段落已去除页眉页脚。 max_chars: 单个知识片段的字符数上限，默认 800。 overlap_chars: 相邻片段的字符重叠量，默认 120。
Returns: 知识片段列表，每项含起止偏移、所属章节标题与顺序号。
Raises: ValueError: max_chars 不大于 overlap_chars 时无法保证片段向前推进。 """ ```
文档字符串用中文书写，专有名词保留英文原文，例如 pgvector、MinIO。术语必须与项目术语表一致，资料切分后的检索单元统一写作知识片段，不得混用切片、分段、知识块等写法。

## 2.5 异常处理与日志

后端统一使用业务异常基类 AppError，它携带错误码、HTTP 状态码与面向用户的提示文案。业务代码抛业务异常，框架层在全局异常处理器中把业务异常转成统一响应体，把未捕获异常记录为错误日志并返回通用提示。禁止在路由层用 try 包裹全部逻辑后再返回字符串。
错误码按五位数字分段，前两位标识类别。10 段表示参数与请求格式问题，20 段表示鉴权与权限问题，30 段表示外部能力问题，40 段表示算法与质量门禁问题，50 段表示内部与数据问题。当前使用中的码值包括 10001 参数校验失败、20001 未登录或登录态失效、20002 无权访问该资源、30001 OCR 识别服务失败、30002 大模型调用超时、40001 资料质量不达标、40002 知识点质检未通过、50001 数据库写入失败。新增错误码必须在本节登记后再使用，禁止在代码里出现未登记的数字码。
日志使用结构化输出，每条至少包含时间、级别、日志名、请求标识、用户引用、业务对象标识、耗时与错误码。用户引用只记录用户标识的不可逆摘要前八位，不记录原始标识。日志级别按用途划分：INFO 记录关键业务节点，包括任务创建、状态流转、判题完成；WARNING 记录可恢复的异常，包括 AI 判题超时转待重新判题、外部调用重试；ERROR 记录需要人工介入的失败；DEBUG 只用于本地开发，不得进入测试与生产环境。
日志禁止记录以下内容：学习资料全文、题目与参考答案全文、用户作答原文、访问令牌与刷新令牌、明文用户标识、数据库口令与第三方密钥。排查文本相关问题时记录长度、片段数量、匹配度、判分来源这类可量化字段即可。写入日志前统一经过脱敏函数，脱敏规则变更必须有对应测试用例，见第 4.2 节。

## 2.6 前端规范

小程序端按页面、业务组件、组合式函数、状态与请求封装五部分组织。页面只负责布局与事件绑定，可复用的展示逻辑下沉为业务组件，横切逻辑写进组合式函数。基础交互组件直接使用 Wot Design Uni，不在项目内重复实现按钮、弹窗一类控件。一个组件文件超过 300 行时必须在同一次改动中拆分，拆分后的子组件放在同名目录下。
状态管理使用 Pinia，按领域划分为资料、练习、诊断报告与用户四个 store。跨页面共享的数据才进 store，仅单页面使用的状态留在页面内部。持久化只允许保存登录态、未提交的作答草稿与用户偏好三类数据，资料与题目不进本地存储。store 内的行动函数必须可被单元测试直接调用，不在其中直接发起网络请求，网络调用统一放在 api 目录下由 store 引用。
请求封装集中在 src/api 下，统一处理基础地址、鉴权头、超时、错误码映射与重试。普通请求超时设为 15 秒，资料上传与出题请求设为 60 秒。重试只对幂等的查询请求和携带幂等键的写请求开放，连续失败两次后停止并提示用户。页面卸载时取消未完成的请求，避免回调写入已销毁的页面状态。
小程序端的性能约束有三条。数据更新必须合并后一次调用 setData，禁止在循环中逐条更新视图数据，长列表每页加载 20 条并做窗口回收。页面滚动回调中只允许更新视图层变量，禁止在其中执行计算、请求或格式化。主包体积必须控制在 2 MB 以内，资料管理与诊断报告页面放入分包，图片上传前在本地压缩到长边 1600 像素以内。

## 2.7 格式化与静态检查工具

格式与静态检查的争议交给工具裁决，评审时不再讨论缩进、引号与导入顺序。后端使用 Ruff 同时承担格式化与静态检查，类型检查使用 mypy，安全扫描使用 bandit，依赖漏洞检查使用 pip-audit。前端使用 ESLint 检查代码质量、Prettier 统一格式、vue-tsc 检查类型。
后端配置集中在 backend/pyproject.toml。Ruff 的行宽设为 100，目标版本设为 py311，启用的规则集包括 E、F、I、N、UP、B、SIM、S、RUF 与 ASYNC。mypy 先对 app/core、app/core/algorithms 与 app/services 强制严格模式，禁止未标注类型的函数定义，其余模块在后续版本逐步纳入。本地执行以下命令，任一条非零退出即视为不合格。
``bash cd backend ruff format --check . ruff check . mypy app bandit -r app -ll pip-audit --strict ``
前端配置集中在 miniprogram 目录。ESLint 启用 vue3 与 typescript 推荐规则集，并在提交前对暂存文件自动修复；Prettier 与 ESLint 的格式规则合并配置，避免两者互相覆盖；vue-tsc 的检查范围覆盖 src 全量，模板内的类型错误同样按错误处理。
``bash cd miniprogram pnpm run lint pnpm run type-check pnpm run test:unit ``
工具版本锁定在依赖锁文件中，本地与流水线使用同一版本。调整规则集、行宽或忽略清单属于影响全组的改动，必须单独提交并在合并请求中说明影响面，禁止在业务改动中顺带修改规则配置。确实需要忽略某一行时使用带规则名的行内忽略并在同一行末尾写明原因，禁止使用文件级忽略。

# 3 源代码管理

源代码管理处理的是并行开发下的冲突、追溯与准入问题。本章规定分支形态、命名与提交格式、合并请求流程、评审判定标准、版本打标方式，以及哪一类改动必须由谁批准。这些约定同时是可自动检查的：分支保护、提交信息校验与代码所有权都由仓库服务端配置强制，不依赖成员记忆。

## 3.1 仓库与分支模型

本项目采用精简版 Git Flow，保留五类长期或短期分支，去掉原版中面向多版本并行的支持分支，与单主链、四到六周的交付节奏匹配。分支流转关系见 [图 3-1：分支流转图]，其中 main 与 develop 为长期分支，feature、release、hotfix 为按需创建并在合并后删除的短期分支。
图 3-1　分支流转图
日常开发路径是从 develop 切出 feature 分支，完成一个任务编号对应的工作后通过合并请求合回 develop。develop 上积累够本次发布需要的全部能力后，切出 release 分支进入冻结期，冻结期内只接受缺陷修复，修复同时合回 develop。release 验证通过后合入 main，在 main 上打版本标签，再从标签构建部署产物。线上出现问题时从 main 的标签切出 hotfix 分支，修复验证后同时合回 main 与 develop，并补打补丁版本标签。
各分支的职责、来源、合并目标与保护规则见表 3-1。保护规则由仓库服务端强制执行：受保护分支禁止直接推送，禁止强制推送，禁止删除，合并前必须通过流水线必需的检查项。
表 3-1　分支职责与保护规则
| 分支 | 职责 | 来源 | 合并目标 | 保护规则 |
| --- | --- | --- | --- | --- |
| main | 唯一可发布状态，每次提交都可交付 | release 或 hotfix | 无 | 禁止直接推送；需 1 名代码所有权人批准且必需检查项全绿；禁止强制推送与删除；标签只能在此分支打 |
| develop | 集成开发状态，功能在此汇合 | main 初始化后长期存在 | 无 | 禁止直接推送；需 1 名评审人批准且必需检查项全绿 |
| feature/* | 单个任务编号对应的功能开发 | develop | develop | 无强制保护；存在关联合并请求时禁止强制推送 |
| release/* | 发布冻结与回归验证，只接受缺陷修复 | develop | main 与 develop | 禁止直接推送；需 2 名评审人批准；合并信息中必须写明版本号 |
| hotfix/* | 线上问题紧急修复 | main 的版本标签 | main 与 develop | 禁止直接推送；需 2 名评审人批准；必须附回归测试用例 |

分支生命周期有两条补充规则。feature 分支的存活时间应当控制在五个工作日以内，超过时需要在看板卡片上说明原因并考虑拆分为多个任务；长期分支落后 develop 超过三十个提交时应当先同步再继续开发，减少合并时的冲突面。合并策略上，feature 合入 develop 使用压缩合并并保留提交信息中的任务编号，release 与 hotfix 合入 main 使用普通合并以保留完整历史。

## 3.2 分支命名与提交信息规范

分支名必须携带任务编号，格式为类型加斜杠加任务编号加短描述，短描述用小写英文与连字符，长度不超过五个单词。合法示例包括 feature/ZL-104-material-split、fix/ZL-118-mastery-decay、release/v1.2.0、hotfix/ZL-131-judge-timeout。分支名不得包含中文、空格、日期字符串或大写字母，日期信息由提交时间承担。
提交信息采用统一格式，由类型前缀、可选范围、标题、可选正文与可选关联行组成，各部分之间用空行分隔。类型前缀的取值与用途见表 3-2。范围填写受影响的模块名，取值限于 api、services、algorithms、integrations、models、miniprogram、deploy、ci、docs 之一。
表 3-2　提交类型前缀
| 前缀 | 用途 | 示例标题 |
| --- | --- | --- |
| feat | 新增对用户可见的能力 | feat(algorithms): 增加知识点质检门禁 |
| fix | 修复缺陷 | fix(services): 修复交卷后掌握度未更新 |
| refactor | 不改变外部行为的重构 | refactor(repositories): 统一查询的用户条件 |
| test | 补充或调整测试 | test(algorithms): 补齐判题阈值边界用例 |
| docs | 只改文档 | docs(process): 补充评审严重级别定义 |
| chore | 构建、依赖与杂项 | chore(deps): 升级向量检索依赖版本 |
| perf | 性能优化 | perf(integrations): 复用大模型连接池 |
| ci | 流水线与脚本 | ci: 集成测试阶段增加向量扩展初始化 |
| revert | 回滚既有提交 | revert: 回滚 ZL-127 的缓存改动 |

标题长度上限为 50 个字符，中文按一个字符计，句末不加句号，使用祈使语气的动词开头，读完能回答"这次提交做了什么"。正文用于说明为什么这样改，每行不超过 72 个字符，可以分段。关联行固定写法为 Refs 加任务编号，存在缺陷单据时补一行 Fixes 加缺陷编号。下面是一个完整示例。
```text fix(services): 修复交卷后掌握度未更新
离线判题结果写入时未携带判题来源，掌握度计算取不到置信权重， 导致同一知识点多次答对后数值不变。改为在判题结果中显式记录来源， 并在掌握度入口对缺失来源的记录按最低权重处理，避免脏数据放大分值。
Refs: ZL-118 Fixes: BUG-046 ```
提交粒度要求一次提交只做一件事，且能通过现有测试。禁止把格式化全仓、依赖升级与业务改动混在同一次提交里，混合提交会让缺陷定位与回滚都变得困难。确需重排格式时单独提交，标题使用 chore 前缀并在正文说明范围。提交作者信息必须是本人姓名拼音与项目邮箱，禁止使用默认的机器名。

## 3.3 合并请求流程与模板

所有进入 develop、release 与 main 的改动都必须通过合并请求，受保护分支不接受任何形式的直接推送。仓库服务端已开启分支保护，直接推送会被拒绝，绕过保护的做法不在本文档允许范围之内。工作流程是：feature 分支完成后推送远端，创建合并请求并填写模板全部小节，指定评审人，等待必需检查项通过并获得批准后合并，合并后删除源分支。
合并请求在开工时可以先以草稿状态创建，用于让评审人提前看到方向，草稿状态不触发部署阶段但会运行静态检查与单元测试。改动超过 400 行有效差异时应当拆分，拆分依据按层或按功能边界，确实无法拆分时在描述中说明理由与风险。
合并请求模板包含七个小节，创建时逐项填写，没有内容的小节写"无"，不留空。变更目的与关联任务，写清任务编号与要解决的问题。变更内容，按模块列出改动要点。影响面自查，按变更文件数、对外接口、数据模型、鉴权与用户隔离、外部依赖、回滚难度、影响范围七项逐条回答。验证方式与证据，列出本地执行的命令与结果、相关测试用例名称、必要时的截图。风险与回滚方案，写明失败时的回滚步骤。自查清单，勾选格式化与静态检查已通过、新增逻辑有对应测试、无调试代码与敏感信息、文档与代码同步。评审关注点，主动指出希望评审人重点看的位置。
影响面自查中的七项任一项命中时，合并请求按高风险处理：改动跨越两个以上模块；修改对外接口的入参、出参或状态码；修改数据库表结构或向量索引；触碰鉴权、用户隔离与密钥处理；引入新的第三方依赖或升级核心依赖；改动难以回滚或需要人工修复数据；失败时会影响全部用户的主链。高风险合并请求需要两名评审人批准，其中至少一人是第 3.6 节定义的代码所有权人，并且必须给出回滚方案。
评审通过的判定条件有五条，全部满足才允许合并：必需检查项全部通过，包括格式化、静态检查、类型检查、单元测试、集成测试与前端检查；无未解决的阻断级或重要级评论；达到人数要求的批准，一般变更一名，高风险变更两名；与目标分支无冲突；改动范围与关联任务一致，没有夹带无关修改。同一名成员不得批准自己创建的合并请求，也不得通过再次推送来消解已提出的阻断级意见。

## 3.4 代码评审要点

评审分三个维度独立扫描，评审人按维度组织意见，避免只盯着格式。正确性与边界维度关注空值与缺省处理、集合越界、数值取整与阈值比较、异步任务的状态流转、并发写入同一记录、资源释放。安全与用户隔离维度关注所有面向用户数据的查询是否带了用户条件、是否存在通过资源标识直接查询导致的越权、密钥与口令是否硬编码、SQL 与向量查询是否参数化、日志是否泄漏资料与作答原文。与计划一致性维度关注改动是否收敛在关联任务范围内、算法层是否保持纯函数、外部能力是否仍通过接口抽象调用。
问题按三个级别标记，级别决定处理方式与是否放行合并。阻断级指破坏主链正确性、导致数据错误或泄漏、绕过鉴权与门禁的问题，必须修复后才能合并。重要级指在特定条件下会出错或明显增加维护成本的问题，包括缺少边界用例、异常被吞掉、重复实现已有工具函数，同样要求修复后合并。次要建议指命名偏好、局部可读性、注释措辞一类不影响正确性的意见，合并前不强制处理。
单次评审报告中次要建议的数量上限为 5 条。超出部分只汇总条数并说明可以在后续改动中一并处理，不逐条展开。这条限制的目的在于把评审注意力留给正确性与安全问题，避免评审演变成风格逐行校对。评审人对同一处代码提出三次以上往返意见仍无法达成一致时，交由技术负责人裁定，裁定结论记入合并请求。
评审时限按工作日计算，评审人应当在收到请求后 24 小时内给出首轮意见，紧急修复按第 6.1 节的响应时限执行。意见必须给出可执行的修改方向或明确的追问，只写"这里不好"的意见视为无效，评审人需要补充理由。评审人应当优先使用仓库的建议功能，无法用建议表达时给出代码位置与替代写法。
评审时自动跳过三类内容：由框架生成的代码与模式定义，包括 OpenAPI 与 Pydantic 生成部分；构建产物与静态资源打包文件；已由工具强制统一的格式问题。跳过不等于不检查，相关风险仍由对应维度的实质审查承担。

## 3.5 标签与版本基线

版本号采用语义化版本，格式为主版本、次版本、修订号三段。主版本在出现不兼容的对外变更时提升，次版本在新增向后兼容能力时提升，修订号在向后兼容的缺陷修复时提升。标签格式为小写 v 加版本号，例如 v1.0.0，必须使用附注标签并写明本次发布的主题。
release 分支创建后先打候选标签，格式为版本号加 rc 加序号，例如 v1.0.0-rc.1。候选标签对应的产物部署到预发环境完成回归，回归通过后合入 main，在 main 上打正式标签，从该标签构建的镜像才允许部署到生产环境。补丁发布使用修订号递增。main 上的标签禁止移动或重新指向其它提交，需要修正时提升修订号重新发布。
发布说明由部署与文档负责人编写，固定包含五节：版本与日期；新增能力，按用户可见的功能描述并标注需求编号；修复的缺陷，列出缺陷编号与一句话现象；已知问题，由未关闭的缺陷直接导出；升级注意事项，说明数据库迁移、环境变量与配置变更。发布说明存放在 docs/release 下，文件名与标签一致。
数据库迁移与版本号必须对齐。每个包含结构变更的发布都必须在 backend/migrations 下带一个 Alembic 迁移脚本，迁移脚本经过评审并在测试环境验证升级与降级两条路径。镜像标签同时写入版本号与提交标识的前八位，部署脚本按提交标识回滚到上一个可用镜像，因此标签、镜像与提交三者可以互相核对。

## 3.6 代码所有权

代码所有权通过仓库根目录的 .github/CODEOWNERS 文件声明，命中路径的改动被自动请求对应负责人评审，负责人未批准时分支保护不允许合并。三类高风险改动的归属与评审要求单独明确，它们分别是算法核、鉴权与用户数据隔离、部署配置，见表 3-3。
表 3-3　代码所有权归属与评审要求
| 路径 | 责任范围 | 所有权人 | 评审要求 |
| --- | --- | --- | --- |
| backend/app/core/algorithms/ | 资料分块算法、知识点质检、题目质检、判题阈值与匹配、掌握度计算 | TechLead、SecLead | 双人评审，其中必须包含TechLead；改动阈值默认值时必须附测试用例与依据 |
| backend/app/core/security.py、backend/app/api/deps/、backend/app/repositories/ | 登录态与令牌、权限校验、用户数据隔离 | SecLead、TechLead | 双人评审；必须包含针对越权访问的负向用例 |
| deploy/、.github/workflows/、backend/Dockerfile、backend/migrations/ | 容器编排、流水线、镜像构建、数据库迁移 | DevOpsLead、SecLead | 双人评审；必须附回滚步骤与迁移降级验证结果 |
| backend/tests/、pyproject.toml 中的覆盖率配置 | 测试用例与覆盖率门槛维护 | Reviewer | 单人评审 |
| miniprogram/ | 小程序端全部代码 | SecLead | 单人评审 |
| docs/、.gitignore、.pre-commit-config.yaml | 项目文档与仓库级配置 | DevOpsLead | 单人评审 |

算法核的改动要求双人评审，原因是阈值与权重直接影响判题结论与诊断报告的可信度，单人容易带着原假设确认自己的参数。鉴权与用户隔离的改动要求双人评审并强制附负向用例，目的是阻断水平越权这一类难以通过功能测试发现的问题。部署配置要求双人评审，原因是它同时影响全部环境与线上可用性，回滚窗口很短。
所有权人名单变更由技术负责人提出并更新 CODEOWNERS 文件，变更本身按文档改动走评审。所有权人因故无法在 24 小时内响应时，可以授权另一名成员临时代行批准，授权必须在合并请求中明确写出，不得默认生效。

# 4 测试工具

测试工具的选择围绕一个目标：让核心算法与外部服务之间的边界足够清晰，从而让判定结论可以脱离网络与数据库被反复验证。本章依次说明测试分层、单元测试范围、覆盖率门槛、接口与集成测试的环境隔离、小程序端验证方式、性能测试场景，并把全部门槛汇总为一张可执行的表。

## 4.1 测试分层与职责

后端测试分为单元、集成、接口与端到端四层，加上独立执行的性能测试。单元测试只覆盖纯函数与离线逻辑，不连接数据库、缓存与外部服务，单个用例执行时间在毫秒级，全部单元测试在 30 秒内跑完。集成测试覆盖仓储层与数据库交互、队列投递与消费、对象存储读写，使用真实的 PostgreSQL、Redis 与 MinIO 容器。接口测试使用 FastAPI 的测试客户端，覆盖鉴权、参数校验、错误码、分页与幂等，同样运行在容器化依赖之上。端到端测试覆盖小程序端的核心用户路径，以自动化脚本配合人工回归完成。
用例数量分布按金字塔要求控制：单元测试占六成以上，集成与接口测试合计约三成，端到端用例控制在一成以内。这个比例决定了缺陷被发现的位置，也反向说明为什么算法层要保持纯函数。如果把判分逻辑写进服务层并直接访问数据库，边界用例的编写成本会高到没人愿意写。
测试责任人分工固定。Reviewer负责测试用例设计与门槛维护，各模块实现者在提交时附带对应测试，算法核的用例由实现者编写、由Reviewer复核边界覆盖是否完整。集成测试用例在功能开发完成后由实现者与本模块之外的一名成员共同确认。

## 4.2 单元测试

单元测试使用 pytest 8.x，测试文件放在 backend/tests/unit 下，文件名与被测模块对应。用例命名采用 test 加行为加条件加期望的三段式，让人不看代码就知道断言在验证什么。每个用例遵循准备、执行、断言三段结构，禁止在一个用例里断言多个互不相关的行为。共享的构造逻辑抽成 fixture，数据差异用参数化表达，参数化用例超过二十组时应当按等价类拆分为多个用例。
测试替身的使用有明确边界。算法层是纯函数，不需要替身。需要替身的只有三类：外部能力适配器以固定返回值的桩实现替换；时间与随机数以可注入的时钟与固定种子替换；对象存储与队列以内存实现替换。禁止用模拟库对被测函数自身的内部调用做断言，这类测试会随重构失效，且并不验证真实行为。
本项目有五块纯函数计算核属于必测范围，它们的输入、输出与测试手段见表 4-1。这五块与概要设计说明书第 7.1 节的纯函数清单一致，任何一块新增分支时必须在同一次改动中补充用例。
表 4-1　必测纯函数计算核清单
| 计算核 | 输入 | 输出 | 测试手段 | 覆盖要求 |
| --- | --- | --- | --- | --- |
| 资料分块算法 | 段落序列、片段长度上限、重叠长度、标题层级标记 | 知识片段列表，含起止偏移、所属章节与顺序号 | 等价类划分配合边界值：片段长度取 1、恰等于上限、上限加一；重叠取 0 与上限；单段超长强制截断；孤立短段合并；空输入与全空白输入 | 分支覆盖 100% |
| 知识点质检 | 候选知识点列表（名称、层级、来源覆盖计数）、章节统计、阈值配置 | 质检结论、逐项得分、不通过原因 | 决策表覆盖四个条件的全部组合：数量区间、层级深度、命名可读性、章节覆盖率 | 判定覆盖 100% |
| 题目质检 | 候选题集合（题干、答案、来源片段、题干向量）、相似度阈值 | 保留题目集与逐题剔除原因 | 等价类划分四类异常：重复题、答案冲突、缺少来源、表述歧义；相似度函数以桩替换返回固定值 | 条件组合覆盖 |
| 判题阈值与匹配 | 作答文本、参考答案、采分点及权重、否定词表、相似度上下阈值 | 得分、命中与遗漏要点、是否转 AI 判题 | 边界值取匹配度恰等于下阈值与上阈值；决策表覆盖四种转 AI 条件，即离线判错、落在不确定区间、存在多个等价表达、无法严格匹配；否定词反转专项用例 | 条件组合覆盖 |
| 掌握度计算 | 答题记录序列（对错、时间、题型、判题来源）、当前时间、衰减系数 | 零到一之间的掌握度数值与四档档次 | 性质测试配合参数化用例：近期答对后数值不降低、闲置越久数值越低、无记录与全错记录的边界；档次临界值 0.40 与 0.70 的判定 | 分支覆盖 100% |

判题阈值与匹配这一块的测试重点在不确定区间的边界。相似度落在下阈值与上阈值之间时转 AI 判题，恰等于下阈值按离线判错处理，恰等于上阈值按离线判对处理，三个边界各有独立用例。否定词的用例需要覆盖仅有否定词不同、其余文字完全一致的成对输入，验证两者得分方向相反。掌握度计算的衰减形式为加权正确率乘以时间衰减因子，默认衰减系数取 0.023，对应约 30 天的半衰期，权重方面离线确定判分取 1.0、AI 判题取 0.8、用户自评与待重新判题取 0.5，测试用例覆盖闲置 3 天、7 天、30 天与 300 天四种情形，并对无答题记录返回未学档次的约定做单独断言。
白盒度量按课程要求执行。对上述五块计算核绘制控制流图，按环路复杂度等于边数减节点数加二、也等于判定节点数加一的关系计算复杂度，并依据独立路径集设计用例，保证每条独立路径至少执行一次。三个复杂度最高的函数作为重点对象：资料分块算法的主切分函数、判题匹配函数与掌握度聚合函数，目标是把环路复杂度分别控制在 12、10 与 8 以内，超过时先做函数拆分再补用例。控制流图以图片形式随测试报告归档，路径覆盖情况在报告中逐条列出。

## 4.3 覆盖率工具与阈值

覆盖率使用 pytest-cov 统计，必须同时开启分支统计，只统计行覆盖会漏掉条件分支只走一半的情况。统计范围限定在 backend/app，测试代码与工程脚本不计入。执行命令如下，其中失败阈值由流水线强制，本地执行同一命令可以提前发现问题。
``bash cd backend pytest tests --cov=app --cov-branch --cov-report=term-missing --cov-fail-under=80 coverage json -o coverage.json python ../tooling/check_coverage.py --report coverage.json ``
阈值分两档。全局行覆盖不低于 80%，分支覆盖不低于 70%。关键模块适用更高阈值：backend/app/core/algorithms 行覆盖不低于 95%、分支覆盖不低于 90%；backend/app/core/security.py 行覆盖不低于 95%；backend/app/services 行覆盖不低于 85%。分模块阈值由 tooling/check_coverage.py 读取覆盖率报告逐项校验，任一模块低于阈值即判定失败，脚本输出的达标表随流水线日志留档。
排除清单集中维护在 backend/pyproject.toml 的覆盖率配置中，当前只包含四类：应用启动装配文件、任务消费进程入口、迁移脚本的环境装配模块、由 Pydantic 生成的模式定义目录。新增排除项必须走合并请求，在描述中写明将被排除的行数、排除理由与替代验证方式，并经Reviewer批准。禁止用行内标注跳过覆盖来规避阈值，确有不可达的防御分支时必须注明原因，且单个文件内的行内跳过标注不得超过 3 处，超过时按评审意见处理。
覆盖率不是唯一门槛。覆盖率上升但用例集中在取值简单的路径上时，需要补充边界与异常路径用例，评审人有权在使用覆盖率数据之前先检查用例分布。流水线记录每次改动的覆盖率数值，出现明显下降的改动需要在合并请求中说明原因。

## 4.4 接口与集成测试

接口测试使用 FastAPI 的测试客户端，通过 HTTP 层调用真实路由，验证鉴权、参数校验、状态码、响应结构与错误码。集成测试使用容器化的 PostgreSQL 16 加 pgvector、Redis 7 与 MinIO，验证仓储查询、向量检索、缓存与对象读写是否符合预期。两类测试共用一套 fixture，放在 backend/tests/integration/conftest.py 中。
环境隔离有明确做法。数据库每个测试会话建一次结构与向量扩展，每个用例在事务中执行并在结束时回滚，保证用例之间不互相污染。Redis 使用独立编号的库并在每个用例前清空。MinIO 使用临时存储桶，用例结束删除对象。大模型与 OCR 一律替换为固定返回的假实现，假实现对同一输入返回固定结果，需要模拟超时的场景通过注入延迟开关实现。测试进程内禁止真实联网，conftest 中安装一个拦截网络连接的 fixture，出现外部连接即抛错，这样能避免慢测试与不可控的费用。
必须覆盖的接口行为有五类：未携带令牌访问受保护接口返回 20001；使用甲用户令牌访问乙用户资料返回 20002 或资源不存在，两者都不得返回资料内容；资料上传对零字节文件、超过 50 MB 文件、扩展名与内容不符文件分别返回对应错误码；重复提交同一幂等键返回首次结果且不产生第二条记录；分页参数越界返回参数校验失败而不是空列表。

## 4.5 小程序端测试

小程序端的自动化测试分两层。逻辑层用 Vitest 配合 Vue 测试工具验证组合式函数与纯逻辑，重点覆盖答题计时、答案暂存与恢复、掌握档次到展示文案的映射、请求重试与取消、错误码到提示文案的映射。这些逻辑不依赖小程序运行时，可以完整跑在流水线里。视图层使用小程序自动化工具驱动开发者工具，覆盖导入资料、查看出题进度、作答与交卷、查看判题结果、查看诊断报告并继续练习五条关键路径，验证页面跳转、关键文案与异常提示。
自动化未覆盖的部分用人工回归清单兜底。清单在 release 分支创建时执行一次，包含真机兼容性验证：iOS 与 Android 微信客户端各至少两台机型，覆盖主流分辨率与系统版本，核对长文本与表格资料在作答页的可读性、公式与特殊符号是否遮挡操作、弱网下上传与交卷的提示是否准确。回归结论记入发布说明的已知问题一节。

## 4.6 性能测试

性能测试使用 JMeter 5.6，脚本与结果存放在 backend/perf 下，运行环境独立于测试环境，数据由 tooling/seed_perf_data.py 生成并在压测结束后清理。当前有两个必测场景。
并发交卷判分场景模拟多用户同时提交练习。并发梯度取 50、100 与 200，每个梯度持续 5 分钟，要求客观题判分的响应时间 95 分位不超过 1.5 秒，错误率低于千分之一，每秒事务数不低于 120。主观题比例按三成配置，用于观察转 AI 判题的排队情况，AI 判题超时的请求必须落到待重新判题状态而不是直接失败。
大文件解析排队场景同时上传 20 个 20 MB 至 50 MB 的资料文件，观察 Redis 队列的任务积压深度、消费进程的内存占用与任务终态。要求任务不丢失、无重复消费，全部任务在 30 分钟内进入成功或失败终态，失败任务必须给出可读的失败原因。执行命令与结果归档方式如下。
``bash jmeter -n -t backend/perf/submit_grading.jmx -l backend/perf/result.jtl -e -o backend/perf/report ``
性能结果写入发布说明，出现未达标项时在发布说明中记录偏差幅度、原因与处理计划，不得以环境波动为由直接删除记录。

## 4.7 质量门禁阈值汇总

质量门禁分布在提交、合并、构建与发布四个环节，任一环节失败即阻断后续步骤，不允许人工跳过。前三个环节由流水线自动执行，发布环节在预发环境完成回归后由技术负责人确认。全部阈值与失败处理方式见表 4-2。
表 4-2　质量门禁阈值汇总
| 环节 | 工具 | 阈值 | 失败处理 |
| --- | --- | --- | --- |
| 提交前 | pre-commit 触发 Ruff 格式化、ESLint 修复、文件尾与密钥检查 | 全部通过 | 拒绝提交，修复后重新提交 |
| 静态检查 | Ruff 检查、mypy、vue-tsc | 错误数为 0 | 阻断合并 |

例外处理只有一条通道。环境依赖缺失、偶发失败用例或已记录的局限导致必需检查项无法通过时，必须在合并请求中列出例外项、原因、规避方式、责任人与修复排期，并获得技术负责人批准后由管理员临时放行。每次放行记录到 docs/process/exceptions.md，同一例外项连续放行两次后必须转为缺陷单据跟踪。

# 5 持续集成

持续集成把前面几章的约定落到自动执行的流水线上，让规则不依赖人的记忆。本章说明流水线阶段划分、触发规则与环境映射、构建产物与部署方式，以及本地提交前需要执行的检查。流水线未覆盖的约定不写入本章，避免出现无法验证的条款。

## 5.1 流水线设计

本项目使用 GitHub Actions 作为持续集成平台，选择理由有三条。代码仓库已在 GitHub，流水线与代码同处一个平台，密钥与环境保护规则可以与分支保护直接联动。矩阵构建、依赖缓存与容器服务开箱可用，不需要为项目自建构建机。容器化依赖可以在作业中以服务容器方式声明，PostgreSQL 加 pgvector、Redis 与 MinIO 的启动配置可以随代码一起版本化。自建流水线服务需要额外维护一台常驻机器与插件升级，对四到六周的课程周期不划算，因此不作为本期方案。
流水线分为五个阶段，前四个阶段在合并请求上执行，第五阶段只在受保护分支推送时执行。阶段一是静态检查，Ruff 格式化检查、Ruff 检查、mypy、bandit 与 pip-audit 并行运行，前端 ESLint 与 vue-tsc 同步执行。阶段二是单元测试，在 Python 3.11 与 3.12 两个版本上并行运行并汇总覆盖率，同时校验分模块阈值。阶段三是集成与接口测试，使用服务容器启动依赖，先执行数据库迁移再运行用例。阶段四是镜像构建与健康检查探测。阶段五是部署，按分支映射到对应环境。任一阶段失败即中断后续阶段，不产生镜像，也不执行任何部署动作。
流水线配置文件放在 .github/workflows 下，属于代码所有权中部署配置一类，改动需要双人评审。下面的片段给出静态检查与单元测试两个作业的骨架，实际文件还包含服务容器、缓存与产物上传配置。
```yaml name: backend-ci on: pull_request: push: branches: [main, develop, "release/*"]
jobs: static: runs-on: ubuntu-latest steps:
* uses: actions/checkout@v4
* uses: actions/setup-python@v5
with: python-version: "3.11"
* run: pip install -e "backend[dev]"
* run: ruff format --check backend/app
* run: ruff check backend/app
* run: mypy backend/app
* run: bandit -r backend/app -ll
* run: pip-audit --strict
unit: runs-on: ubuntu-latest strategy: matrix: python-version: ["3.11", "3.12"] steps:
* uses: actions/checkout@v4
* uses: actions/setup-python@v5
with: python-version: ${{ matrix.python-version }}
* run: pip install -e "backend[dev]"
* run: pytest backend/tests/unit --cov=app --cov-branch --cov-fail-under=80
`

## 5.2 触发规则与环境映射

触发规则按分支与事件组合定义，映射关系见表 5-1。设计原则是让反馈速度与分支风险成反比：越接近发布的阶段执行越完整的检查，越早期的阶段只跑必要项，避免每次推送都等待全量流水线。
表 5-1　触发规则与环境映射
| 触发条件 | 流水线范围 | 目标环境 | 审批要求 |
| --- | --- | --- | --- |
| feature 分支的合并请求 | 静态检查、单元测试、集成与接口测试 | 不部署 | 无 |
| develop 分支推送 | 全部阶段加镜像构建 | 测试环境自动部署 | 无 |
| release 分支推送 | 全部阶段、镜像构建与端到端回归 | 预发环境 | 技术负责人 1 人 |
| main 分支推送 | 全部阶段、镜像构建与发布产物归档 | 生产环境 | 技术负责人与部署负责人各 1 人 |
| v 开头的标签推送 | 归档镜像、发布说明与测试报告 | 不部署 | 无 |

开发环境供成员本地联调使用，由 Docker Compose 在本地启动，不纳入流水线部署范围。测试环境使用 develop 分支最新通过的镜像，允许随时重建与清空数据。预发环境使用 release 分支镜像，数据脱敏后从生产抽样一份，用于验证迁移与回归。生产环境只接受 main 分支标签对应镜像，部署窗口在发布说明中约定。

## 5.3 构建产物与部署方式

构建产物有三类：后端镜像、小程序端构建产物与测试报告。镜像标签同时写入版本号与提交标识前八位，镜像推送到私有镜像仓库并保留最近十个版本。小程序端产物以构建产物形式上传归档，包含提交标识与构建时间，用于核对线上版本与仓库状态。测试报告包含单元测试结果、覆盖率报告与性能测试报告，随流水线留档，性能报告按第 4.6 节要求附控制流图与路径覆盖清单。
部署步骤固定为四步。先拉取目标镜像并核对标签与提交标识的对应关系。再执行数据库迁移，在部署目录内把结构升级到最新版本，迁移失败时中止部署并保留旧容器运行。然后以滚动方式替换后端服务，健康检查连续通过三次后视为部署成功。收尾阶段更新部署记录，写入版本号、提交标识、执行人与时间。
回滚按镜像回滚与迁移回滚两条路径分别执行。代码问题直接切回上一版本镜像，通常在两分钟内完成。涉及结构变更的回滚必须使用迁移的降级路径，降级前先备份受影响表，不可逆的迁移在发布说明中标注为不可降级，并要求在部署窗口内完成数据校验。小程序端的回滚通过重新上传历史构建产物实现，审核期间的问题通过服务端配置开关降级，因此所有影响答题主链的新能力都必须带服务端开关。
部署脚本必须幂等，重复执行不产生额外副作用。脚本中不得硬编码口令与地址，全部从环境变量与密钥管理功能读取，环境变量样例文件随仓库维护但只放占位值。

## 5.4 本地前置检查

本地开发需要在提交前完成与流水线一致的检查，减少无效的流水线运行。项目使用 pre-commit 框架管理钩子，成员在克隆仓库后执行一次安装命令，安装命令会同时拉取钩子依赖。
``bash pip install pre-commit pre-commit install --install-hooks pre-commit run --all-files ``
钩子包含以下内容：文件尾空行与行尾空白修正；YAML 与 JSON 语法检查；禁止提交私钥与凭据文件；禁止提交超过 5 MB 的文件；对暂存的 Python 文件执行 Ruff 格式化与检查；对暂存的前端文件执行 ESLint 修复；对变更的算法层文件执行对应单元测试的快速子集。钩子失败时提交被拒绝，允许使用跳过参数绕过，但绕过记录会出现在流水线结果中，绕过次数在每周同步会上核对。
跨平台注意事项有三条。仓库使用 .gitattributes 统一文本文件为 LF 行尾，避免 Windows 与其它系统之间反复出现整文件差异导致格式化检查失败。钩子脚本用 Python 入口实现，不依赖 bash，保证在 Windows 本地与 Linux 流水线上行为一致。路径处理使用标准库的路径对象，禁止在脚本中拼接反斜杠或正斜杠字面量，避免跨平台失效。

# 6 缺陷跟踪

缺陷跟踪处理的是问题从被发现到被关闭这段时间里的信息完整性与责任归属。本章规定缺陷的来源与分级、报告必须包含的要素、状态流转与关闭条件，以及缺陷记录与代码评审、发布流程之间的衔接方式。本项目缺陷记录使用与任务卡片同一看板，缺陷编号以 BUG 加三位序号编排，与任务编号分别计数。

## 6.1 缺陷来源与分级

缺陷有六个来源：流水线执行的失败、代码评审中标记的阻断级与重要级问题、测试执行的用例失败、性能测试未达标、预发与生产过程的监控告警、用户反馈。任何来源发现的问题都必须建单，只在聊天中口头说明不算记录。
严重程度分四级，判定依据是影响范围与是否存在替代路径，响应与修复时限见表 6-1。分级由发现人初判，测试负责人可以调整，出现分歧时由技术负责人裁定。严重程度与处理优先级不是同一个维度，S3 缺陷如果集中在即将发布的版本上，可以被提升为优先处理。
表 6-1　缺陷严重程度与响应时限
| 级别 | 判定标准 | 典型情形 | 响应时限 | 修复时限 |
| --- | --- | --- | --- | --- |
| S1 | 阻断主链，或产生错误数据、越权可见 | 判题结论错误、甲用户可见乙用户资料、资料导入后无法进入下一步、服务整体不可用 | 2 小时 | 当日 8 小时内 |
| S2 | 主要功能受损且无替代路径 | 出题任务长时间停留在处理中、诊断报告缺失、受保护分支的保护规则失效 | 4 小时 | 24 小时 |
| S3 | 次要功能受损或有替代路径 | 某类格式解析偶发失败、报告页展示错位、提示文案不准确 | 1 个工作日 | 3 个工作日或下个发布版本 |
| S4 | 不影响功能的体验问题 | 文案错别字、间距不一致 | 下个发布版本前 | 随版本处理 |

S1 与 S2 的修复走 hotfix 分支，修复提交必须包含一个先失败后通过的复现用例，回归验证由发现人或测试负责人执行，修复人与验证人不得是同一人。S3 与 S4 随正常任务流程处理，在卡片上标注缺陷编号。

## 6.2 缺陷报告要素

缺陷报告必须包含七项要素，缺项的报告在评审时按不合格退回。环境与版本，写清后端版本号或提交标识前八位、小程序基础库版本、微信客户端版本与运行环境名称。前置条件，写清账号状态、资料状态与必要的配置项。复现步骤，按编号列出每一步的操作与输入，粒度细到可以照做。预期结果与实际结果，分别描述，实际结果附错误码与提示文案。复现率，写必现，或给出出现次数与尝试次数的比例。证据，附日志片段与请求标识、接口响应、页面截图或录屏，日志中涉及用户数据时按第 2.5 节的脱敏要求处理。影响范围与首次出现版本，说明受影响的用户范围以及从哪个版本开始出现。
报告中的描述必须可被验证。只写"上传有问题"不合格，需要写清是哪一类格式、多大体积、在什么网络条件下的上传出现了什么提示。定位过程中的假设与猜测写在评论中，不写进报告正文，避免后续读者把推测当成结论。

## 6.3 缺陷生命周期

缺陷状态包括新建、已确认、处理中、待验证、已关闭与已驳回，流转关系见 [图 6-1：缺陷状态流转图]。状态由责任人推进，每次状态变更必须写明变更理由，无法复现的缺陷在确认阶段退回并记录尝试过的环境与步骤。
图 6-1　缺陷状态流转图
完整路径是：发现人建单并填写七项要素，状态为新建；测试负责人或模块责任人确认后进入已确认，确认不成立时驳回并说明依据；修复人在卡片上领取任务后进入处理中，同时给出预计完成时间；修复完成后进入待验证，并在卡片中附上修复提交、复现用例名称与自测结果；验证人在测试环境按复现步骤与新用例验证，通过则关闭，不通过则退回处理中并补充新的复现信息。
关闭条件有三条，必须同时满足：修复提交的关联行写入了缺陷编号；复现用例已入库且先失败后通过的过程可查；在测试环境按原步骤验证通过。仅修复代码而没有用例的缺陷不允许关闭，原因是没有用例就无法防止回归。
缺陷统计按发布周期汇总三项指标：缺陷密度，以每个需求条目的缺陷数计；平均修复时长，按严重程度分组统计；重开率，统计关闭后重新打开的缺陷占比。重开率高于一成时，在同步会上复盘定位环节的问题。

## 6.4 与代码评审、发布流程的衔接

代码评审中发现的阻断级与重要级问题一律建缺陷单，评审评论不能替代缺陷记录。这样做有两个直接好处：缺陷的修复过程可以进入统计，问题不会因为合并请求关闭而失去跟踪。评审中的次要建议不建单，按第 3.4 节的上限处理。
发布前设置缺陷门槛：S1 与 S2 必须归零；S3 不超过 5 个且有明确排期与责任人；S4 允许保留并全部写入发布说明的已知问题一节。门槛未达成时不允许进入预发回归，技术负责人批准例外时需要在发布说明中记录。
修复与发布的时间关系也有约定。冻结期内的 S1 与 S2 通过 hotfix 直接进入发布版本，S3 与 S4 默认进入下一个版本，仅当修复局限在单文件且带完整用例时可以申请进入当前版本。缺陷修复提交与发布版本的对应关系在打标签时核对，核对结果写入发布说明。

# 7 文档与协作约定

本章说明哪些文档必须产出、在什么时机产出、每类文档至少要写清什么，以及这份规范自身如何修订。文档要求的出发点是让交付物与实现保持可核对，避免出现代码与说明脱节、验收时无法追溯依据的情况。

## 7.1 文档类型与触发时机

需要产出的文档分五类，触发时机、责任人与存放位置见表 7-1。技术方案用于高风险变更；接口文档由代码自动生成并配合变更记录；缺陷报告与发布说明在上一章已有规定；运行手册面向部署与故障处理。
表 7-1　文档类型、触发时机与责任人
| 文档类型 | 触发时机 | 责任人 | 存放位置 |
| --- | --- | --- | --- |
| 技术方案 | 改动命中第 3.3 节七项影响面任一项且跨两个以上模块时，在开工前完成 | 提出人编写，技术负责人批准 | docs/design 下按任务编号命名 |
| 接口文档 | 接口新增或变更时随合并请求更新 | 后端负责人 | 运行时自动生成的 OpenAPI 文件与 docs/api 下的变更记录 |
| 缺陷报告 | 发现缺陷时立即建立 | 发现人 | 看板缺陷卡片，要素见第 6.2 节 |
| 发布说明 | 每次打发布标签时 | 部署与文档负责人 | docs/release 下按版本号命名 |
| 运行手册 | 首次部署前建立，部署方式或环境变量变更时更新 | 部署与文档负责人 | deploy 目录下的 README |

文档与代码同步的原则是在同一改动内完成。代码改动导致已有文档失效时，必须在同一次合并请求中更新文档，不允许以后续补充为由留到下一轮。评审人有权以文档不同步为理由提出重要级意见。

## 7.2 文档模板要点

技术方案的模板要求写清五项：要解决的问题与不做的事情边界；涉及的接口、数据模型与迁移方案；可测试性说明，点明可独立测试的纯函数与外部依赖的替换方式；失败与回滚方案；验收方式与可执行的验证命令。方案中出现的阈值必须给出依据，不得只写结论。
接口文档的模板要点有四条：请求路径、方法与鉴权要求；关键入参与出参及其约束，包含取值范围与单位；错误码清单与触发条件；调用示例与幂等要求。字段级明细由代码生成，文档只写关键字段与变化说明。
缺陷报告的模板即第 6.2 节的七项要素，模板中把七项列为固定小节，避免遗漏。发布说明的模板即第 3.5 节的五节结构，模板内附检查项，确认已知问题已从看板导出后再发布。运行手册包含环境变量清单、部署与回滚命令、常见故障的处理步骤与联系人。

## 7.3 规范自身的维护与修订

本文档的修订走合并请求流程，修订请求必须写明改动条目、改动理由与对现有代码的影响面。影响组织方式与门槛数值的修订需要两名成员批准，其中一名必须是技术负责人；纯表述修正与示例补充由文档所有权人批准即可。每次修订在文首的修订记录表增加一行，版本号按次版本递增，并在发布说明中登记。
例外申请是修订之外的临时通道。成员认为某一条约定在当前情境下不适用时，可以在合并请求中申请例外，写明条目编号、场景、替代做法、影响范围与有效期，由技术负责人批准。有效期最长为一个发布周期，到期后必须转为正式修订或停止例外。全部例外记录集中保存在 docs/process/exceptions.md 中，按季度复审。
规范每季度复审一次，复审内容包括：阈值是否仍与当前代码规模匹配；工具版本与规则集是否需要调整；是否存在反复被申请例外的条目需要修订；来自演练的约定在本项目中是否仍然适用。复审结论写入本文档的修订记录，未产生修订时也记录一次复审结论，便于验收人确认规范处于维护状态。
本附录记录本项目的工程规范在流程层面的来源。演练与智练是两个不同的业务，本附录只记录流程约定与判定标准，不搬运演练场景的业务内容，也不照搬其技术选型。附录中的表与正文表格分别编号。

## A.1 演练概况

演练来自学习通 AI 实践练习《软件工程全链路实战：从需求到发布的团队协作演练》，练习开放时间为 2026-09-08 14:09 至 2027-01-01 00:00，达标线为 60 分，多次练习取平均分作为最终成绩。本轮已完成两次完整作答，两条记录都跑完七个节点，成绩见 A.4 节。成绩取数通过课程进度接口读取历史作答记录完成，未消耗练习次数。
演练采用角色扮演方式推进。学生本人扮演技术组长，负责技术决策、规范制定、代码评审、进度跟踪与团队协调；产品经理、开发工程师、测试工程师与旁白由 AI 扮演，分别负责提出需求与验收成果、执行编码与响应评审、执行测试与反馈缺陷、推进场景叙述与节点切换。整条练习线围绕技术组长与三个 AI 角色之间的对话展开，其中两个节点要求提交作品文件而非对话。
七个里程碑按顺序解锁，前一个节点的解锁条件达成后才开放下一个节点。节点 01、02、04、05、07 为情景对话节点，单节点对话轮次上限为 30 轮；节点 03 与节点 06 为作品提交节点。每个节点按各自的评分维度给分，维度与权重在节点内固定。

## A.5 演练中被本项目沿用的约定

有五类约定从演练直接沿用，并在本文档中换成本项目的工具与路径。分支策略沿用了以长期集成分支加短期功能分支为核心的结构，本项目把分支类型精简为五类，并按分支风险设置不同的保护级别。提交信息沿用了必须关联任务编号的做法，本项目把任务编号格式固定为 ZL 加三位序号，并要求写入分支名与合并请求标题。评审要点沿用了按正确性、安全、计划一致性三个维度扫描并设定次要建议上限的做法，本项目把上限固定为 5 条并补充严重程度的三级定义。
门禁阈值思路的沿用体现在两个方面：必需检查项全绿才允许合并，例外必须书面登记并指定责任人与修复排期；高风险变更需要双人签批并附回滚方案。本项目把高风险变更的判定改写为七项影响面自查，把双人评审落到算法核、鉴权与用户数据隔离、部署配置三类路径上。缺陷生命周期沿用了发现、记录、修复、验证四个阶段与关闭条件，本项目补充了严重程度分级、响应时限与发布前缺陷门槛。
有三类内容明确不沿用。演练的业务场景与业务对象不进入本项目的任何文档与代码。演练场景的服务端技术栈与本项目不同，本项目的服务端、小程序端与工具链按决策基线选取，不以演练为参照。演练使用的任务看板与缺陷工具属于课程环境，本项目使用自己维护的看板文件与缺陷编号规则，只借用卡片字段的组织方式。
