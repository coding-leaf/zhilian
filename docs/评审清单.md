# 评审清单（中期质量检查 · 增量规范）

| 项 | 值 |
| --- | --- |
| 编制时间 | 2026-10-04 |
| 编制来源 | 中期质量检查 M1-005 改进项 |
| 适用范围 | 所有 PR/MR 评审 |
| 维护责任 | TechLead + Reviewer |

---

## 1 总则

> **评审原则**：对事不对人；控制时长；以本检查清单为准；避免风格争论。

---

## 2 评审检查清单（8 项）

> 每项评审**必须**逐项走查，不能跳过。

### 2.1 正确性

- [ ] 逻辑是否符合需求？
- [ ] 测试断言是否反映真实业务行为？
- [ ] 是否漏掉边界条件？
- [ ] 是否漏掉错误推测？

### 2.2 设计

- [ ] 职责是否单一？
- [ ] 耦合是否合理？
- [ ] fixture 复用是否到位？
- [ ] 测试结构是否清晰？

### 2.3 可读性

- [ ] 命名是否符合规范（被测对象 + 条件 + 期望）？
- [ ] 结构是否清晰？
- [ ] 注释是否准确？
- [ ] docstring 是否聚焦**被测对象契约**？

### 2.4 健壮性

- [ ] 异常处理是否完整？
- [ ] 边界是否覆盖？
- [ ] 错误码是否一致？
- [ ] 日志是否得当？

### 2.5 安全与性能

- [ ] 是否有注入风险？
- [ ] 权限边界是否守住？
- [ ] SQL 是否合理？
- [ ] 是否有并发缺陷？

### 2.6 测试充分性

- [ ] 关键分支是否覆盖？
- [ ] 等价类 / 边界值 / 错误推测 / 路径覆盖是否到位？
- [ ] 是否锁住**正确行为**而非**当前行为**？

### 2.7 可维护性

- [ ] 是否易于扩展？
- [ ] 是否易于调试？
- [ ] 断言失败时定位是否清晰？

### 2.8 文档与追溯

- [ ] 是否关联 P 编号 / 缺陷编号？
- [ ] 后续维护者能否理解「为什么这样写」？

## 3 Mock/Stub 评审子清单

> **关键检查项**（来自 M1-005 改进）

### 3.1 是否使用了反模式

| 反模式 | 替代 |
| --- | --- |
| `class _StubClass(RealClass): __init__: skip` | `MagicMock(spec=RealClass)` |
| `iter([...])` 隐式 StopIteration | `itertools.cycle(...)` |
| `_private_field` 内部状态断言 | `m.method.assert_called_once()` |

### 3.2 spec 配置

- [ ] mock 是否配置 `spec=`？
- [ ] 是否 mock 了足够的方法？

### 3.3 上下文管理器

- [ ] `get_session` 等 contextmanager 是否被正确模拟？
- [ ] yield 前后是否清理 mock 状态？

---

## 4 异常处理评审子清单

### 4.1 捕获类型

- [ ] 是否避免 `except Exception`？（除顶层兜底）
- [ ] 是否捕获具体异常类型？
- [ ] 是否有用 `from exc` 保留原因链？

### 4.2 测试断言

- [ ] `pytest.raises` 是否断言具体类型？
- [ ] 是否验证 `__cause__` 链路？

---

## 5 状态机评审子清单

> **关键检查项**（来自 PR4 评审发现）

### 5.1 状态机迁移

- [ ] 是否覆盖所有状态？
- [ ] 是否覆盖**非法迁移**拦截？
- [ ] 是否覆盖**并发场景**？
- [ ] 是否覆盖**事务边界**？

### 5.2 事务边界

- [ ] try 块是否覆盖**所有可能失败**的位置？
- [ ] 二次校验是否纳入事务？
- [ ] rollback 是否在**所有抛错路径**？

## 6 问题分级

| 级别 | 含义 | 处理 |
| :---: | --- | --- |
| **🔴 阻塞** | 必须修复后才能合并 | PR 必须修改后再次评审 |
| **🟠 重要** | 应该修复但不阻塞 | 作者可在后续 PR 修复，但需登记在案 |
| **🟡 建议** | 可改进项 | 评审人建议，作者可自由决定 |

---

## 7 评审结论模板

每个 PR 必须给出以下三种结论之一：

| 结论 | 含义 | 下一步 |
| --- | --- | --- |
| ✅ **通过** | 无阻塞 / 无重要问题 | 合并 |
| 🟡 **修改后通过** | 有重要问题但可在同一 PR 内修复 | 作者修改后评审人复核 → 合并 |
| ❌ **不通过** | 有阻塞问题 | PR 必须重写或拆分 |

---

## 8 评审时长预算

| PR 行数 | 评审时长上限 |
| ---: | ---: |
| 0-200 行 | 15 min |
| 200-400 行 | 25 min |
| 400-600 行 | 35 min |
| 600-1000 行 | 45 min |
| > 1000 行 | ⚠️ 必须拆分 |

> **不推荐拆分**：单 PR > 600 行评审疲劳，> 1000 行强制拆分。

---

## 9 评审记录产出

每次评审必须输出：

| 项 | 内容 |
| --- | --- |
| **评审记录** | 作者讲解 → 评审人提问 → 问题讨论 → 结论 |
| **问题清单** | 分级（🔴/🟠/🟡）+ 描述 + 行号 + 建议 |
| **评审结论** | ✅ 通过 / 🟡 修改后通过 / ❌ 不通过 |
| **合并授权** | 主评审 + 副评审签字 |

> **位置**：`中期质量检查/正式代码评审/<PR_编号>_评审记录.md`

## 10 评审反模式

| 反模式 | 反模式后果 |
| --- | --- |
| 评审流于形式（仅自动检查） | 错过设计/逻辑问题 |
| 评审时间过长（> 45 min） | 评审人疲劳，问题被放过 |
| 评审人「LGTM」但无具体意见 | 等于未评审 |
| 评审人**作者自评** | 失去制衡 |
| 评审后未回归验证 | 修复引入新 bug |
| 「可以合并」但 CI 不绿 | 机器门禁失效 |

---

## 11 评审纪律

| 原则 | 含义 |
| --- | --- |
| **对事不对人** | 问题以「PR + 行号」描述 |
| **控制时长** | 单 PR ≤ 25 min，4 PR 总 ≤ 120 min |
| **以检查清单为准** | 8 项清单逐项走查 |
| **避免风格争论** | 仅讨论 ruff 强制项 |
| **自动检查先于人工** | 9 项机器门禁全绿后再评审 |

---

## 12 复评纪律

| 项 | 要求 |
| --- | --- |
| 复评触发 | 修改后通过 / 不通过 修改后 |
| 复评范围 | 仅评审**修复的部分**，不重审全 PR |
| 复评签字 | 原主评审 + 副评审 |
| 复评结论 | 通过 / 不通过 |
